## Огляд

Файл формує поведінкову документацію з джерела, розділяє захищений контекст і редаговані частини через `splitProtected` та `insertProtected`, а для секції API окремо збирає опис публічних можливостей через `buildApiSection`. Для тексту документації враховуються `capTimeoutToDeadline`, `stripLeadingPreamble`, `scoreDoc`, `hasCompleteCommentDocumentation`, `commentDocumentationMode` і `insertTestScenarios`, а генерація та завершення батча проходять через `DEFAULT_LOCAL_MODEL`, `generateDoc`, `prepareBatchItem` і `finishBatchItem`; кешування діє в межах одного прогону, щоб повторні звернення не дублювали роботу.

## Поведінка

`DEFAULT_LOCAL_MODEL` задає локальну модель за замовчуванням, а `generateDoc` використовує її як базовий шлях генерації: спочатку читає джерело й пов’язані факти, потім обирає режим побудови документа, збирає секції, рахує якість і лише після цього вирішує, чи результат достатньо сильний. Якщо документ уже існує, захищений блок зберігається окремо й переноситься в готовий Markdown без втрати змісту.

`prepareBatchItem` готує той самий вхідний набір даних для batch-шляху, але без самого LLM-виклику. Це потрібно, щоб один спільний preflight, один і той самий факт-лист і ті самі правила для захищеної секції працювали однаково і в послідовній, і в batch-обробці. `finishBatchItem` потім приймає уже готову відповідь моделі й завершує той самий ланцюжок очищення, збирання та оцінки, що й послідовний шлях.

`commentDocumentationMode` вирішує, чи можна довіритися суто авторським коментарям, чи треба додавати LLM-повідомлення, чи переходити в fallback-режим. Для повністю прокоментованого коду це зменшує кількість генерації, а для змішаних файлів зберігає короткий машинний допис там, де людських пояснень недостатньо. `hasCompleteCommentDocumentation` є перевіркою, яка дозволяє взагалі обійти LLM, коли коментарі вже покривають потрібний зміст.

`splitProtected` і `insertProtected` працюють як парний механізм для секції «Призначення»: перша відокремлює її з наявного документа, друга повертає її назад у фіксоване місце після заголовка. Це дає змогу зберігати важливий людський контекст без залежності від того, який режим генерації був обраний. Те саме спрощує повторні прогони, коли треба оновити решту документа, не чіпаючи цей блок.

`capTimeoutToDeadline` узгоджує per-call таймаути з глобальним дедлайном, щоб генерація не стартувала, коли бюджет уже вичерпано. Цей контроль використовується на всіх LLM-етапах, тож одна й та сама часова межа діє послідовно для всього прогону. Коли ліміт вичерпано, це поводиться як transient-зрив, щоб система могла спробувати ще раз у наступному проході.

`stripLeadingPreamble` прибирає чатову «обгортку» на початку відповіді, а `insertProtected` та `buildApiSection` далі працюють уже з очищеним текстом. Такі мета-фрази модель інколи додає перед контентом, і без цього очищення вони потрапили б у секції документа як зайвий шум. Саме тому `buildApiSection` спирається на текст без preamble і на вже збережений захищений блок, щоб зібрати стабільну публічну частину документа.

`scoreDoc` є завершальним детермінованим фільтром: він звіряє зібраний Markdown із фактами файлу, оцінює повноту змісту й фіксує проблеми, не покладаючись на нову генерацію. Результат цього скорингу впливає на `generateDoc` і `finishBatchItem`: якщо якість нижча за поріг, документ позначається як degraded і може бути перегенерований у наступному проході. Важливі анкори з вихідного файлу мають зберігатися дослівно, а пропуски у верифікації відображаються саме як недостача змісту, а не як зміна структури.

`buildApiSection` додає до документа секцію про публічний API лише там, де це дійсно потрібно: покриті коментарями експорти описуються без додаткової генерації, а прогалини доповнюються LLM. Це зменшує ризик галюцинацій і робить секцію ближчою до фактичного коду. У результаті API-частина стає частково детермінованою, а частково доповненою лише там, де бракує людського опису.

`generateDoc` є головним оркестратором одного файлу: він збирає вхід, обирає режим, будує документ, рахує score і повертає Markdown разом із метаданими виконання. Якщо файл підтримує повний коментований шлях, може спрацювати без LLM або з мінімальними викликами; якщо ні — переходить у one-shot або оркестровану генерацію. Усе це працює в межах локального прогону та спирається на кешування в межах цього ж запуску, щоб не робити зайвих повторів.

`insertTestScenarios` додає окрему секцію з test-сценаріями детерміновано, уже після основного збирання документа. Це потрібно, щоб сценарії не залежали від LLM і не змішувалися з наративом про код. У batch- і one-shot-шляхах ця секція лишається стабільною частиною фінального Markdown.

`finishBatchItem` завершує той самий життєвий цикл, що й `generateDoc`, але для вже отриманого batch-відповіді. Воно використовує ті ж правила очищення, ту ж структуру секцій і той самий скоринг, щоб batch-результат можна було порівнювати з послідовним шляхом без окремої логіки.

## Публічний API

- capTimeoutToDeadline — Ріже базовий per-call таймаут під залишок бюджету до дедлайну.
Без дедлайну — базовий ліміт; після дедлайну — 0 (виклик не має стартувати).
- stripLeadingPreamble — R9: зрізає провідні чат-преамбули й дубль назви секції з початку тексту.
Ітерується, поки перший непорожній рядок лишається мета-нарацією — модель
інколи ставить дві поспіль («Як технічний письменник…» + «Ось оновлений…»).
- splitProtected — Відокремлює захищену секцію `## Призначення` (Варіант B). Межа — наступний `## `
(H2); `###`+ усередині не обривають блок.
- insertProtected — Вставляє захищений блок `## Призначення` одразу після H1 (фіксована позиція).
- scoreDoc — Stage 2.5 — детермінований скоринг (0 токенів): перевіряє вихід проти фактів.
- buildApiSection — Stage 1/3 (гібрид doc-files, ADR 260719-2155): «Публічний API» — покриті
JSDoc-описом експорти рендеряться дослівно (`renderApiLine`, 0 токенів, 0
галюцинацій), LLM викликається лише на прогалини (`isApiGap`). Якщо прогалин
немає — секція збирається БЕЗ жодного LLM-виклику. Єдиний непокритий
експорт (як і раніше) лишається описаним лише в Поведінці — окремого виклику
на секцію з одного рядка не варте.
- hasCompleteCommentDocumentation — Чи коментарі автора повністю покривають машинну документацію: header дає
«Огляд», а змістовні описи всіх public API — відповідну секцію. У такому
разі LLM не потрібна: текст зберігається дослівно для JS, Rust і Python.
- commentDocumentationMode — Вибирає гібридний режим для повністю прокоментованого source. Короткий
header майже напевно є pointer-ом, а середній header разом із явним flow у
коді потребує короткого LLM-доповнення. Детальний наратив лишається 0-LLM.
- insertTestScenarios — Додає test-сценарії до one-shot/batch-документа. Для unsupported мов основний
Markdown ще повертає LLM, але test-секція лишається виключно JS-рендером.
- DEFAULT_LOCAL_MODEL — Дефолтна модель: N_CURSOR_DOCGEN_MODEL → resolveModel('min') (→ N_LOCAL_MIN_MODEL).
Без хардкод-fallback: модель налаштовує кожен локально (`N_LOCAL_MIN_MODEL`); якщо
нічого не задано — порожньо, і preflight оркестратора фейлить гучно (а не шле
запит до неіснуючої моделі).
- generateDoc — Головний API: файл → md-дока з det-оцінкою.

Local-only (ADR 260610-2228): жодних cloud-ескалацій і pre-route — будь-який
файл генерується локальною моделлю. Якщо det-score нижче порогу, один retry
з вищою температурою (best-of-2); якщо й він не допоміг — результат
позначається `degraded`, рішення про перегенерацію приймає batch/користувач.
- prepareBatchItem — T8 (2b-batch, рішення Р): підготовка ОДНОГО item-у для `submitBatch` — та сама
pre-send guard і той самий факт-лист/one-shot messages, що й `oneShotDoc`/
`generateDoc`, але БЕЗ виклику LLM (виклик робить batch-шар одним `submit` на
всі файли разом). Кидає ту саму помилку pre-send guard, що й `generateDoc`
(класифікується `permanent` у batch-оркестраторі — skip, не помилка прогону).
- finishBatchItem — T8 (2b-batch): постобробка ОДНОГО результату `submitBatch` — той самий фініш,
що й `oneShotDoc`/`finishUnsupported`/det-скорер, тільки без LLM-виклику
(текст уже отримано з batch-у). Judge-гейт (Stage 3) у batch-шляху НЕ
викликається (мінімальний обсяг T8 — генерація; judge лишається опційним
розширенням послідовного шляху).
