## Огляд

`generateDoc` і пов’язані з ним публічні кроки формують один стабільний Markdown-документ для коду, щоб поведінкова документація лишалась узгодженою між звичайним і batch-прогоном. Захищені секції виділяються та вставляються окремо через `splitProtected` і `insertProtected`, тому їх вміст зберігається між оновленнями. У межах одного прогону використовується кешування, щоб повторні звернення не розмивали результат і не створювали зайвих перегенерацій.

## Поведінка

Генерація йде як конвеєр із кількома режимами, але спільний результат завжди збирається в один Markdown-документ і далі оцінюється детерміновано. `generateDoc` читає джерело, підтягує факти, за потреби зберігає захищене `## Призначення` з наявної доки, обирає режим через `commentDocumentationMode` і далі або збирає текст без LLM, або проганяє його через одну чи кілька модельних стадій. `prepareBatchItem` бере той самий preflight і той самий факт-лист, але лише готує вхід для batch, а `finishBatchItem` потім застосовує той самий фініш, score та збереження захищеного блоку вже до готової відповіді батчу.

`commentDocumentationMode` розводить повністю прокоментовані джерела на швидкий шлях без генерації та на змішаний шлях, де частина тексту зберігається дослівно, а частина добудовується моделлю. `hasCompleteCommentDocumentation` визначає, чи можна довіритися авторським коментарям повністю; якщо так, `commentOnlyDoc` складає документ лише з них і детермінованих фактів. Якщо ні, `generateDoc` переходить до оркестрованого або one-shot сценарію, а `DEFAULT_LOCAL_MODEL` задає локальну модель за замовчуванням для цього шляху.

`splitProtected` і `insertProtected` керують незмінною секцією `## Призначення`: на вході вона вирізана з наявної доки, а на виході повертається на фіксоване місце після H1, щоб не губити людський контекст між перегенераціями. Цей самий блок переноситься через усі режими, включно з batch, тому повторна генерація не стирає ручне призначення. Маркер з повідомлень `` тут зберігається як частина такого захищеного контексту, а не як окрема логіка документа.

`stripLeadingPreamble` прибирає chat-преамбули, щоб у документ не потрапляли службові вступи моделі; далі очищений текст може проходити через `buildApiSection`, `scoreDoc` або `finishBatchItem`. `scoreDoc` звіряє зібраний Markdown із фактами, секціями та наявними анкорами й повертає детерміновану оцінку та коди проблем, які вирішують, чи потрібен retry або degraded-стан. Саме ця оцінка є спільною мовою між послідовним і batch-потоком.

`buildApiSection` працює як міст між фактичним екстрактором і текстом документа: покриті JSDoc-описом елементи переносяться дослівно, а модель залучається лише для прогалин. Це зменшує ризик галюцинацій і тримає public API секцію стабільною між прогонами. У повністю прокоментованих файлах цей механізм може бути взагалі не задіяний, бо `hasCompleteCommentDocumentation` переводить генерацію на безLLM-режим.

`insertTestScenarios` завжди додає окрему детерміновану секцію сценаріїв у фінальний Markdown, незалежно від того, чи текст решти документа прийшов із one-shot, orchestrated або batch. `generateDoc`, `prepareBatchItem` і `finishBatchItem` усі зводяться до того самого правила: тестова секція формується JS-рендером окремо, щоб не залежати від моделі й не змішувати її з основною структурою документа.

## Публічний API

- capTimeoutToDeadline — Ріже базовий per-call таймаут під залишок бюджету до дедлайну.
Без дедлайну — базовий ліміт; після дедлайну — 0 (виклик не має стартувати).
- stripLeadingPreamble — R9: зрізає провідні чат-преамбули й дубль назви секції з початку тексту.
Ітерується, поки перший непорожній рядок лишається мета-нарацією — модель
інколи ставить дві поспіль («Як технічний письменник…» + «Ось оновлений…»).
- splitProtected — Відокремлює захищену секцію `## Призначення` (Варіант B). Межа — наступний `## `
(H2); `###`+ усередині не обривають блок.
- insertProtected — Вставляє захищений блок `## Призначення` одразу після H1 (фіксована позиція).
- scoreDoc — Stage 2.5 — детермінований скоринг (0 токенів): перевіряє вихід проти фактів.
- buildApiSection — Stage 1/3 (гібрид doc-files, ADR 260719-2155): «Публічний API» — покриті
JSDoc-описом експорти рендеряться дослівно (`renderApiLine`, 0 токенів, 0
галюцинацій), LLM викликається лише на прогалини (`isApiGap`). Якщо прогалин
немає — секція збирається БЕЗ жодного LLM-виклику. Єдиний непокритий
експорт (як і раніше) лишається описаним лише в Поведінці — окремого виклику
на секцію з одного рядка не варте.
- hasCompleteCommentDocumentation — Чи коментарі автора повністю покривають машинну документацію: header дає
«Огляд», а змістовні описи всіх public API — відповідну секцію. У такому
разі LLM не потрібна: текст зберігається дослівно для JS, Rust і Python.
- commentDocumentationMode — Вибирає гібридний режим для повністю прокоментованого source. Короткий
header майже напевно є pointer-ом, а середній header разом із явним flow у
коді потребує короткого LLM-доповнення. Детальний наратив лишається 0-LLM.
- insertTestScenarios — Додає test-сценарії до one-shot/batch-документа. Для unsupported мов основний
Markdown ще повертає LLM, але test-секція лишається виключно JS-рендером.
- DEFAULT_LOCAL_MODEL — Дефолтна модель: N_CURSOR_DOCGEN_MODEL → resolveModel('min') (→ N_LOCAL_MIN_MODEL).
Без хардкод-fallback: модель налаштовує кожен локально (`N_LOCAL_MIN_MODEL`); якщо
нічого не задано — порожньо, і preflight оркестратора фейлить гучно (а не шле
запит до неіснуючої моделі).
- generateDoc — Головний API: файл → md-дока з det-оцінкою.

Local-only (ADR 260610-2228): жодних cloud-ескалацій і pre-route — будь-який
файл генерується локальною моделлю. Якщо det-score нижче порогу, один retry
з вищою температурою (best-of-2); якщо й він не допоміг — результат
позначається `degraded`, рішення про перегенерацію приймає batch/користувач.
- prepareBatchItem — T8 (2b-batch, рішення Р): підготовка ОДНОГО item-у для `submitBatch` — та сама
pre-send guard і той самий факт-лист/one-shot messages, що й `oneShotDoc`/
`generateDoc`, але БЕЗ виклику LLM (виклик робить batch-шар одним `submit` на
всі файли разом). Кидає ту саму помилку pre-send guard, що й `generateDoc`
(класифікується `permanent` у batch-оркестраторі — skip, не помилка прогону).
- finishBatchItem — T8 (2b-batch): постобробка ОДНОГО результату `submitBatch` — той самий фініш,
що й `oneShotDoc`/`finishUnsupported`/det-скорер, тільки без LLM-виклику
(текст уже отримано з batch-у). Judge-гейт (Stage 3) у batch-шляху НЕ
викликається (мінімальний обсяг T8 — генерація; judge лишається опційним
розширенням послідовного шляху).
