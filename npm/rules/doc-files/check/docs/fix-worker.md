## Огляд

`fixWorker` існує, щоб у local або cloud через `docgen-pipeline` оновлювати лише справді застарілі файлові доки за поточним `ctx` і окремо прибирати сирітські файли, не роздуваючи роботу на весь checkout. Один attempt відповідає одному rung-у; `tier` і `model` беруться з `ctx`, а success визначає canonical re-detect runner-а. Записані доки реєструються як durable через `ctx.recordDurableWrite`: кожна така дока є самодостатнім кінцевим станом зі свіжим CRC, degraded теж валідна, і rollback провального rung-а її не стирає, тож великий backlog сходиться крок за кроком за кілька прогонів. Очищення сирітських док лишається під звичайним rollback через `ctx.recordWrite`. `crc-mismatch` не закривається детермінованим T0-штампом CRC: свіжий CRC зʼявляється лише разом зі щойно згенерованим вмістом у `stampDoc` всередині `runGenerationBatch`.

## Поведінка

1. `fixWorker` збирає лише ті файлові документи, які реально застаріли, і не розширює обсяг роботи на весь checkout, якщо вхід уже обмежений explicit files або `lint --path`.
2. Для кожної такої доки він фіксує намір запису як durable, щоб новий вміст переживав rollback провального rung-а і міг сходитися поступово за кілька прогонів.
3. Після цього `fixWorker` запускає пакетну генерацію доків для всіх знайдених stale-цілей з урахуванням моделі, tier і дедлайну з поточного контексту.
4. Якщо для батчу доступний timeout, `fixWorker` залишає запас до backstop і припиняє старт нових файлів завчасно, щоб не створювати фоновий батч поверх наступного rung-а.
5. Усередині генерації кожна дока отримує свіжий CRC лише разом із новим змістом, тому `crc-mismatch` не маскується окремим детермінованим штампом.
6. Для сирітських док `fixWorker` окремо реєструє звичайний rollback-намір і запускає очищення таких файлів.
7. У результаті `fixWorker` повертає перелік записаних док як touchedFiles, а сирітські доки прибирає з робочого дерева без durable-збереження.

## Гарантії поведінки

- Власних операцій запису (ФС/БД) у файлі немає; виклики імпортованих модулів можуть писати.
