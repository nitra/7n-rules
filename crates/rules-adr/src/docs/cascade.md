## Огляд

Спільний 2-хвильовий batch-каскад усіх LLM-стадій конвеєра — порт `runWave`/`keyedCascade` (`runCascade` у JS — окремий випадок keyed без використання customId у parse; тут одна функція обслуговує обидва).  tier1-хвиля на ВСІ items → ті, чия відповідь не пройшла parse (мережа чи невалідний вихід), ідуть у tier2-хвилю (лише за `allow_cloud` і наявного tier2) → що лишилось — не потрапляє в результат, conservative fallback застосовує викликач стадії.

## Поведінка

WaveItem і WaveResult описують вхід одного елемента хвилі та його підсумок для наступної стадії: кожен item має окремий результат, а помилка для нього не зупиняє весь каскад.  

ChainRef і SubmitBatchFn зберігають один спільний chain state на всі хвилі прогону, щоб trace не розривався між стадіями; обмін через спільний handle допускає послідовний доступ під час async-диспетчу.  

Stats і CascadeCfg задають стан і межі каскаду для викликача: лічильники накопичуються через усі хвилі, а cloud-друга хвиля може бути повністю відключена. keyed_cascade повертає тільки те, що пройшло хоча б одну хвилю; усе, що не парситься або не проходить обидві стадії, лишається без результату як conservative fallback для вищого рівня.  

extract_json бере лише перший JSON-обʼєкт із тексту; якщо обʼєкта немає або текст містить лише шум, повертається помилка. test_chain не завершує chain trace, тож для нього немає зовнішнього ефекту запису. scripted_submit поводиться як детермінований test double: невідомий запит для пари модель/елемент стає item-помилкою, а chain-дані не впливають на результат.

## Публічний API

- WaveItem — Один item batch-хвилі (порт форми `submitBatch`-item-а).
- WaveResult — Результат одного item хвилі: `Ok(text)` чи `Err(message)`.
- ChainRef — Спільний handle ланцюжка прогону: один на всі хвилі всіх стадій.  # Чому `tokio::sync::Mutex`, а не `std`  `trace::ChainHandle` мутується (`&mut self`) на кожен виклик, а [`SubmitBatchFn`] повертає `BoxFuture<'static, _>` — тобто **Send**-future без запозичень із викликача, тож передати `&mut` усередину неможливо, і handle мусить бути спільним. Бойова реалізація тримає guard **через `.await`** самого `dispatch` (інакше кроки ланцюжка не рахувались би всередині хвилі), а `std::sync::MutexGuard` не `Send` — future перестав би влазити в `BoxFuture`. Плата — послідовність хвиль, якої конвеєр і так дотримується: наступна стадія починається лише після повного результату попередньої.
- SubmitBatchFn — Інʼєкція виконавця хвилі: model-spec + items + ланцюжок → результати. Бойова реалізація — обгортка над `llm_lib::batch::dispatch`; тестова — фейк.  [`ChainRef`] тут не «для повноти»: саме через нього per-item рядки trace усіх хвиль отримують ОДИН `chainId` і наскрізний `chainStep`. Без нього прогін із чотирьох хвиль виглядав би для аналітики як чотири незалежні задачі — та сама межа, що була в JS-оригіналі (`submitBatch` не приймав chain), і саме її знімає chain-API `n7n-llm-lib 0.4`.
- Stats — Лічильники прогону — порт `stats` (мутуються стадіями через каскад).  `Serialize` — не зручність: лічильники дослівно лягають у `extra` підсумкового рядка ланцюжка, який читає зовнішня аналітика, тож імена полів там мусять лишитись JS-камелкейсом (`madrInvalid`, не `madr_invalid`).
- CascadeCfg — Конфіг каскаду однієї стадії.
- keyed_cascade — Порт `keyedCascade`: tier1 → parse → tier2 для невдалих → результат лише для items, що пройшли якийсь тир. `parse` отримує сирий текст і `custom_id` (стадіям gen-MADR/gen-merge валідація залежить від item-а).
- extract_json — Витяг першого JSON-обʼєкта з raw-тексту — порт `extractJson`.
- test_chain — Ланцюжок для тестів каскаду: `end()` на ньому НЕ викликається, тож жодного рядка trace ці тести не пишуть — handle тут лише щоб задовольнити [`CascadeCfg`].
- scripted_submit — Фейковий submit: відповіді за (model, custom_id); відсутній ключ — item-помилка. Рахує виклики хвиль на модель. Ланцюжок ігнорує: нічого не диспатчить, тож і крокам взятись нізвідки.

## Гарантії поведінки

- Власних операцій запису (ФС/БД) у файлі немає; виклики імпортованих модулів можуть писати.
- Містить локальні fail-safe гілки; інші помилки можуть поширюватися назовні.
- Деякі локальні fail-safe гілки повертають порожнє значення (напр. `null`) замість винятку.
