# Відновлення відкритих PR — дизайн

## Мета

Зняти спільний CI-блокер, оновити конфліктні PR #262 і #264 та підготувати
змістовний review PR #263. PR #266 не змінюється.

## Межі та послідовність

1. **CI debt.** Окремий PR лише з виправленнями repo-wide `eslint`, `text` і
   `lint-repo`, які зараз відтворюються на `main`. Він не містить змін бізнесової
   логіки відкритих PR і стає базою для повторного запуску CI.
2. **PR #262 і #264.** Після green CI бази оновити кожну гілку від `main`,
   розв'язати конфлікти та запустити релевантні тести й delta-lint. Їхні зміни не
   об'єднуються в один PR.
3. **PR #263.** Провести read-only review Composer semver, nested workspace
   detection, coverage parser і doc-files extractor. Зауваження оформлюються як
   перелік із пріоритетами; код не змінюється без окремого погодження.
4. **PR #266.** Виключений зі scope: не змінюємо ні код, ні опис, ні статус.

## Підхід

Спочатку фіксуємо точний baseline кожної CI-перевірки на `main`. Для кожного
порушення визначаємо, чи воно є конфігураційним debt, чи потребує локального
рефакторингу; додаємо або коригуємо тести лише коли змінюється поведінка правила.
Після green baseline ребейзимо PR #262 і #264 по одному, не переносячи їхні
зміни в гілку CI debt.

## Перевірка

- CI debt: усі три репозиторні lint-перевірки, targeted tests змінених модулів,
  `bun run test` у пропорційному обсязі, `git diff --check`.
- #262 і #264: їхні заявлені focused suites, delta-lint, changelog check і
  повторний GitHub CI після push.
- #263: diff, тести, ADR та інваріанти manifest/Composer без запису в репозиторій.

## Ризики

Repo-wide lint debt може виявитися навмисною зміною policy або містити багато
незалежних дефектів. У такому разі CI cleanup розбивається на менші самостійні
PR, а оновлення #262/#264 не виконується до появи green бази.
