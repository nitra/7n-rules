## 0. Що сталось на боці `llm-lib` (контекст, не робота цього промту)

workspace із чотирма крейтами:

- **`n7n-harness` 0.1.0 (lib `harness`, package-name ≠ lib-name!)** — НОВИЙ

## 1. `crates/rules-core` — найменша правка, але БЛОКУЄ компіляцію

`rules-core` бере `llm-lib` з `default-features = false` (лише `tiers`) —
жодних інших правок структури тут не буде, лише compile-break від
перейменування `Tier`.

**Знайдений зараз реальний виклик** (перевір, чи не змінилось):
`crates/rules-core/src/concerns/adr_hooks.rs:329`:
```rust
let resolved_model = resolve_model(Tier::Min);
```
→
```rust
let resolved_model = resolve_model(Tier::Local);
```
Це єдине місце `rules-core`, що використовує `llm_lib::tiers` (doc-коментар
модуля, розділ `# resolveModel/isLocalModel → llm_lib::tiers`,
рядки 17–26) — перевір, чи `Tier::Min`/`Tier::Avg`/`Tier::Max` не
згадуються деінде (`grep -rn "Tier::" crates/rules-core/`).

Заразом онови сусідні doc-коментарі й тестові рядки, що згадують
скасований `N_LOCAL_MIN_MODEL` (той самий файл, рядки біля
`capture_backend_status`) — замінити на `N_LOCAL_MODEL`. Це лише текст,
логіки не зачіпає (перевірка інформативна: `pass()` — no-op, доккоментар
модуля).

**Cargo.toml**: `crates/rules-core/Cargo.toml`
```toml
llm-lib = { version = "0.2.4", package = "n7n-llm-lib", default-features = false }
```
→
```toml
llm-lib = { version = "0.3", package = "n7n-llm-lib", default-features = false }
```

## 2. `crates/rules-fix` — основна робота: перехід на `n7n-harness`

### 2.1 Cargo.toml

Додати `n7n-harness` як залежність (package name `n7n-harness`, lib name
**`harness`** — не `n7n_harness`, перевір `[lib] name = "harness"` у
`llm-lib/crates/harness/Cargo.toml`):
```toml
harness = { version = "0.1", package = "n7n-harness" }
llm-lib = { version = "0.3", package = "n7n-llm-lib" }
```
`llm-lib` тут лишається на дефолтних фічах (`agents`) — переконайся, що
**також** увімкнена `fix-agent` (`features = ["fix-agent"]`, або перевір,
чи вже так у поточному `Cargo.toml`): `fix::runner`/`fix::tools`
(`llm-lib/crates/llm-lib/src/lib.rs`, `#[cfg(feature = "fix-agent")]`) —
самі механіка циклу, підключаються лише цією фічею, і `fix-agent` **не**
тягне `agents` автоматично (дві незалежні фічі), а `fix/runner.rs`
використовує `write_guard`/`anchored_edit`, які самі під `agents` — тобто
`rules-fix` потребує **ОБИДВІ** фічі увімкненими одночасно.

### 2.2 Перейменування шляхів імпорту (крейт переїхав, сигнатури здебільшого ті самі)

| Було (`llm_lib::fix::…`) | Стало (`harness::…`) |
|---|---|
| `fix::pipeline::{T0Fn, PipelineDeps, PipelineConfig, run_fix, FixReport, Violation, Fixability, resolve_default_ladder, AttemptContext, AttemptFn, DetectFn}` | `harness::pipeline::{…}` (та сама номенклатура, `T0Fn`/`PipelineDeps`/`AttemptContext` мають НОВІ поля — розділ 2.3) |
| `fix::ladder::{RungTier, AvgBudget, Rung}` | `harness::ladder::{RungTier, RungCapBudget, Rung}` (`AvgBudget` → `RungCapBudget`, конструктор ЗМІНИВСЯ — розділ 2.5) |
| `fix::test_gate::compose_verify_report` | `harness::test_gate::compose_verify_report` (сигнатура **без змін** — 5 параметрів у тому самому порядку, лише крейт інший) |

**Лишається без змін** (не переносити помилково):
- `llm_lib::fix::runner::run_attempt` — лишається в `llm-lib`.
- `llm_lib::fix::tools::build_toolset` — лишається в `llm-lib`.
- `llm_lib::fix::{EditMode, FixDeps, FixRequest, VerifyReport, BoxFuture, FixOutcome, StopReason}` — лишається в `llm-lib` (модуль `attempt.rs`, ре-експортований як `llm_lib::fix::*`).
- `llm_lib::tiers::Tier` — лишається в `llm-lib`, лише плоский тепер.

### 2.3 `src/t0.rs` — найбільша концептуальна зміна: `T0Fn -> EditPlan`

Стара модель: `T0Fn = Arc<dyn Fn() -> BoxFuture<'static, ()>>` — `apply_plan`
пише файли САМ (`std::fs::write`/`remove_file`/`remove_dir_all`) і повертає
лише кількість застосованих операцій. Нова модель (§3.9 спеки, рішення И):
T0 рахує ДЕКЛАРАТИВНИЙ план (`llm_lib::edit_plan::EditPlan`), хост (не T0)
його застосовує — рівно та дірка, яку промпт із самого початку просив
закрити (`T0Fn -> EditPlan`, пункт 1 первинного плану).

`PipelineDeps::t0` тепер `Option<harness::pipeline::T0Step>`, не
`Option<T0Fn>`:
```rust
pub struct T0Step {
    pub plan: T0Fn,              // Arc<dyn Fn() -> BoxFuture<'static, EditPlan>>
    pub prepare: PreparePlanFn,  // Arc<dyn Fn(EditPlan) -> BoxFuture<'static, Result<PreparedPlan, String>>>
    pub commit: CommitPlanFn,    // Arc<dyn Fn(PreparedPlan) -> BoxFuture<'static, Result<Vec<PathBuf>, String>>>
}
```
`prepare`/`commit` — БОЙОВІ обгортки над `llm_lib::write_guard::prepare_edit_plan`/
`commit_edit_plan` (`crates/llm-lib/src/write_guard.rs`), які `harness` САМ
не реалізує (лишається featureless, без `agents`) — це РІВНО те, що
`rules-fix` мусить дописати:

```rust
pub fn prepare_edit_plan(guard: &mut WriteGuard, cwd: &Path, plan: &EditPlan) -> Result<PreparedEditPlan, String>
pub fn commit_edit_plan(guard: &mut WriteGuard, prepared: PreparedEditPlan) -> Result<Vec<PathBuf>, String>
```

Потрібна конвертація `write_guard::PreImage`/`PreparedEditPlan` →
`harness::pipeline::{FilePreImage, PreparedPlan}` (типи harness-івської межі,
доккоментар `PreparedPlan` у `harness/pipeline.rs` прямо описує причину —
harness featureless, не бачить `write_guard`). **Прочитай сам**
`crates/llm-lib/src/write_guard.rs` (конструктор `WriteGuard::new(...)`,
структуру `PreImage`) і `crates/llm-lib/src/journal.rs` (`EditPreImage`,
`FilePreImage`) — вони не повністю задокументовані в цьому промті.

**Що робить сам план (крок `T0Fn::plan`)**: заміни `apply_plan` на функцію,
що будує `EditPlan` з `rules_contract::fix::FileEdit` замість писати файли:

- `FileEdit::Delete { path }` → `FileEditPlan::Delete { path }` — прямий 1:1 мапінг, без проблем.
- `FileEdit::Write { path, content }`, **коли `path` ще НЕ існує** →
  `FileEditPlan::Create { path, content }` — прямий мапінг.
- `FileEdit::Write { path, content }`, **коли `path` ВЖЕ існує** — ⚠️
  **ПІДТВЕРДЖЕНО, це не крайовий випадок, а ОСНОВНИЙ шлях щонайменше 7 із
  10 `NATIVE_FIXES`** (перевірено читанням `crates/rules-core/src/concerns/fix.rs`,
  `fix_env_dremio.rs`, `fix_abie_security.rs` — 2026-08-19): `tauri/gitignore_target`,
  `tauri/linux_deps`, `hasura/internal_urls`, `tauri/cargo_mutants_config`
  (гілка «файл частково є»), `abie/env_dns`, `k8s/dremio_logging`,
  `security/sample_secret` усі йдуть за патерном `std::fs::read_to_string`
  наявного файлу → трансформація вмісту → `FileEdit::Write` ТОГО Ж шляху
  повним новим вмістом (`tauri/gitignore_target` тест
  `gitignore_fix_skips_missing_file_like_js_apply_to_files` прямо доводить:
  фікс працює ЛИШЕ коли файл уже існує, пропускає відсутній). Лише
  `hasura/migrations`/`abie/firebase_hosting` (чистий `Delete`) і перша
  гілка `doc-files/marksman_config`/`tauri/cargo_mutants_config` («файла ще
  нема») відповідають простим `Create`/`Delete`.

  `EditPlan::Create` на наявний файл — це `Err` (доккоментар
  `edit_plan.rs`: «повний перезапис наявного файлу свідомо невиразимий»),
  тож пряме перенесення старого коду впаде на переважній більшості
  власних T0-фіксів `rules-core`. **Обов'язково** реалізуй
  `FileEditPlan::Anchored`-стратегію: прочитай ПОТОЧНИЙ вміст файлу
  (`write_guard`/твій код це вже читає — сам `FileEdit::Write.content` уже
  несе НОВИЙ вміст, старий бере окремим `std::fs::read_to_string` перед
  побудовою плану), візьми якір першого рядка через `crate::anchored_edit`
  (прочитай сам `crates/llm-lib/src/anchored_edit.rs` щодо точної функції
  хешування рядка), постав `new_text` першого рядка = ПОВНИЙ новий вміст
  (документація `AnchoredEdit::new_text` явно дозволяє багаторядковий
  текст: «text зі своїми \n розбивається на кілька рядків файлу»), а решту
  рядків старого файлу познач на видалення (`new_text: None`). Це не
  запасний варіант — це шлях, яким піде БІЛЬШІСТЬ реальних T0-прогонів
  після міграції; тестуй його в першу чергу, не в останню.

### 2.4 `src/attempt.rs` — заповнення нових полів `FixRequest`

`ctx: AttemptContext` (з `harness::pipeline`) тепер несе:
```rust
pub struct AttemptContext {
    pub capture: CaptureFn,
    pub rung: harness::ladder::Rung,   // .tier: RungTier, .model: String, ...
    pub feedback: Option<String>,
    pub violations: Vec<Violation>,
    pub journal: Arc<Mutex<llm_lib::journal::Journal>>,  // НОВЕ
    pub has_next_rung: bool,                              // НОВЕ
}
```

`FixRequest` (`llm_lib::attempt`, він же `llm_lib::fix::FixRequest`) додав
поля — заповни ВСІ:

- **`rung: llm_lib::journal::RungId`** — НОВЕ обов'язкове поле. Мапінг з
  `ctx.rung.tier: harness::ladder::RungTier`:
  ```rust
  fn rung_id_for(tier: harness::ladder::RungTier) -> llm_lib::journal::RungId {
      use harness::ladder::RungTier;
      use llm_lib::journal::RungId;
      match tier {
          RungTier::Local => RungId::LOCAL,
          RungTier::LocalRetry => RungId::LOCAL_RETRY,
          RungTier::CloudMin => RungId::CLOUD_MIN,
          RungTier::CloudAvg => RungId::CLOUD_AVG,
          RungTier::CloudMax => RungId::CLOUD_MAX,
      }
  }
  ```
  (Ідентична приватній `rung_id_for` у `harness/src/pipeline.rs` — копію
  довелось написати, бо приватна.)

- **`tier: llm_lib::tiers::Tier`** — і далі обов'язкове поле, але тепер
  мапінг ЧИСТИЙ (стара «неточність мапінгу», задокументована в наявному
  `rung_tier_to_llm_tier`, ЗНИКАЄ разом із каскадом — Tier тепер плоский,
  1:1 з `RungTier`):
  ```rust
  fn rung_tier_to_tier(tier: harness::ladder::RungTier) -> llm_lib::tiers::Tier {
      use harness::ladder::RungTier;
      use llm_lib::tiers::Tier;
      match tier {
          RungTier::Local | RungTier::LocalRetry => Tier::Local,
          RungTier::CloudMin => Tier::CloudMin,
          RungTier::CloudAvg => Tier::CloudAvg,
          RungTier::CloudMax => Tier::CloudMax,
      }
  }
  ```
  Можеш прибрати старий doc-коментар про «неточність мапінгу» — причина,
  яку він описував (каскадний `resolve_model` міг заїхати не в той тир),
  більше не існує.

- **`output_ceiling: u64`** (замінює `max_tokens: Option<u64>`, поле
  ЗАВЖДИ має значення, не `Option`). Дефолт бере
  `llm_lib::budget::FixPolicy` (`output_ceiling: 1024` local,
  `cloud_output_ceiling: 2048` cloud) — env-оверрайд `N_LLM_FIX_MAX_TOKENS`
  лишається, але тепер підставляється ЗАМІСТЬ дефолту політики, а не як
  `Option`:
  ```rust
  fn output_ceiling(local: bool) -> u64 {
      std::env::var(MAX_TOKENS_ENV).ok().and_then(|v| v.parse::<u64>().ok())
          .filter(|&v| v > 0)
          .unwrap_or_else(|| {
              let p = llm_lib::budget::FixPolicy::default();
              if local { p.output_ceiling } else { p.cloud_output_ceiling }
          })
  }
  ```

- **`tool_result_ceiling: u64`** — НОВЕ обов'язкове поле. Рахується через
  `llm_lib::budget::tool_result_ceiling(context, base_tokens, turns, output_ceiling, rates) -> Result<u64, FitError>`.
  Потрібні: `context` (розділ нижче), `base_tokens` (те саме джерело, що й
  `PipelineConfig::base_tokens` у `config.rs`, розділ 2.6), `turns` =
  `turn_ceiling()` (уже є), `rates` = `llm_lib::budget::Rates::from_env()`.
  **`Err(FitError)` тут — не той випадок, де можна тихо підставити
  дефолт**: спека прямо вимагає валідацію влазання ДО HTTP-виклику (§3.3);
  якщо `tool_result_ceiling` повертає `Err`, `build_attempt_fn` має
  повернути провальний `FixOutcome` з `stop_reason: ProviderError` (чи
  найближчий відповідник) і текстом помилки, а не панікувати й не
  замовчувати.

- **`context: u64`** — вікно контексту РУНГА. `ctx.rung.local` каже,
  локальний рунг чи ні:
  ```rust
  let context = if ctx.rung.local {
      llm_lib::budget::local_capability().map(|c| c.context)
  } else {
      llm_lib::budget::cloud_capability(rung_tier_to_tier(ctx.rung.tier)).context
  }.unwrap_or(/* консервативний дефолт — вибери сам, звір з тим, що робить harness::pipeline::build_predictions для аналогічного випадку */);
  ```

- **`has_next_rung: bool`** — тривіально: `ctx.has_next_rung` (уже готове
  поле контексту, жодних обчислень).

- **`ttft_calibration: bool`** — постав `false` (бойовий attempt, не
  калібрувальний прохід — доккоментар поля в `llm_lib::attempt::FixRequest`
  прямо каже «дефолт — false… true — свідомий вибір викликача для
  калібрувального проходу»).

**Виклик `run_attempt` тепер бере журнал 4-м параметром** (`&mut Journal`,
НЕ `Arc<Mutex<Journal>>`):
```rust
pub async fn run_attempt(req: &FixRequest, deps: FixDeps, tools: ToolServerHandle, journal: &mut Journal) -> FixOutcome
```
```rust
let mut journal_guard = ctx.journal.lock().unwrap_or_else(std::sync::PoisonError::into_inner);
run_attempt(&req, deps, handle, &mut journal_guard).await
```
Це критично: без цього журнальне підключення (задача, яка й відкрила всю
цю серію правок у `llm-lib` — «правки моделі не мають жодної події
журналу») просто НЕ дійде до `rules-fix`, попри те що сам `llm-lib` уже це
вміє.

### 2.5 `src/lib.rs` (публічний вхід `fix_concern`/`fix_concerns`)

`AvgBudget` → `RungCapBudget` (`harness::ladder`), **конструктор
ЗМІНИВСЯ**: `AvgBudget::new(max: u32)` (один параметр, лише кеп
`cloud-avg`) → `RungCapBudget::new()` (без параметрів — одразу капує І
`cloud-avg` (`DEFAULT_MAX_AVG` = 3), І `cloud-max` (`DEFAULT_MAX_CLOUD_MAX`
= 1), обидва дефолтом; `RungCapBudget::with_caps([...])` — якщо потрібні
інші числа). Сигнатура публічної функції:
```rust
pub async fn fix_concerns(keys: &[String], cwd: &Path, files: Option<&[String]>, avg_budget: &mut AvgBudget) -> Vec<ConcernRun>
```
→ тип змінюється на `&mut RungCapBudget`, решта форми лишається (щоб
`rules-cli` міняв мінімум коду). `caller` для trace (нове обов'язкове поле
`PipelineConfig`, розділ 2.6) — заший як константу `"rules-fix"` тут, не
виводь у публічну сигнатуру (мінімізуй blast radius на `rules-cli`), якщо
не з'явиться конкретна причина зробити його параметром.

### 2.6 `src/config.rs` — `build_pipeline_config`, найбільше нових полів

`resolve_default_ladder` **змінив сигнатуру** — тепер `EgressPolicy` другим
параметром і повертає `Result`:
```rust
pub fn resolve_default_ladder(local_rungs: bool, egress: EgressPolicy, cloud_timeout_ms: Option<u64>) -> Result<Vec<Rung>, EmptyLadderError>
```
**АЛЕ**: за новим контрактом `PipelineConfig::ladder` очікує ПОВНУ,
**ще НЕ звужену** драбину (`harness::ladder::build_ladder(&resolve_ladder_models())`)
— звуження тепер робить сам `run_fix` (`select_ladder` за
`config.policy.local_rungs`/`egress`) УСЕРЕДИНІ. Використання
`resolve_default_ladder` тут технічно спрацювало б (подвійне звуження
того самого набору — ідемпотентно), але порушує задокументований контракт
поля і губить `meta.cloud_timeout_ms` (`run_fix` викликає
`select_ladder(&config.ladder, ..., None)` — літеральний `None`, per-concern
`cloud_timeout_ms` нема куди пронести через `PipelineConfig` напряму).

**Рекомендований розв'язок** (зберігає поведінку `meta.cloud_timeout_ms`):
звужуй ladder ТУТ, у `build_pipeline_config`, викликом `select_ladder`
напряму з `meta.cloud_timeout_ms`, і клади РЕЗУЛЬТАТ у `PipelineConfig::ladder`
разом із `policy.local_rungs = true`/`policy.egress = EgressPolicy::AllowCloud`
(щоб внутрішнє повторне звуження `run_fix`-ом було no-op над уже звуженим
набором):
```rust
let ladder = harness::ladder::select_ladder(
    &harness::ladder::build_ladder(&harness::ladder::resolve_ladder_models()),
    !meta.skip_local_tier,
    llm_lib::budget::EgressPolicy::AllowCloud,
    meta.cloud_timeout_ms,
).map_err(|err| /* пробрось як помилку build_pipeline_config, чи що тут доречно */)?;
```

`PipelineConfig` — заповни решту нових полів:
```rust
pub struct PipelineConfig {
    pub cwd: PathBuf,
    pub target_files: Vec<PathBuf>,
    pub fixability: Fixability,
    pub ladder: Vec<Rung>,           // вже звужений (рекомендація вище)
    pub policy: FixPolicy,           // local_rungs: true, egress: AllowCloud, решта — FixPolicy::default() + перевизначення з meta, якщо є відповідник
    pub rates: Rates,                // Rates::from_env()
    pub local_capability: Option<Capability>,  // llm_lib::budget::local_capability()
    pub base_tokens: u64,            // llm_lib::calibration::resolve_base_tokens() з падінням на CONSERVATIVE_BASE_TOKENS — перевір точну назву функції сам (crates/llm-lib/src/calibration.rs)
    pub caller: String,              // "rules-fix"
    pub chain_id: Option<String>,    // None — нова сесія щоразу (без resume у цьому зрізі)
}
```

### 2.7 `src/verify.rs`, `src/detect.rs`, `src/violation_map.rs`

- `verify.rs`: лише `use llm_lib::fix::test_gate::compose_verify_report` →
  `use harness::test_gate::compose_verify_report` — сигнатура НЕ змінилась
  (5 параметрів, той самий порядок), тіло функції чіпати не треба. Другий
  імпорт `llm_lib::fix::{BoxFuture, VerifyReport}` — **не чіпати**, лишається
  в `llm-lib`.
- `detect.rs`: `use llm_lib::fix::pipeline::{DetectFn, Violation as PipelineViolation}`
  → `use harness::pipeline::{DetectFn, Violation as PipelineViolation}` — сама
  логіка `run_canonical`/`target_files_from_violations` не змінюється.
- `violation_map.rs`: `use llm_lib::fix::pipeline::{Fixability, Violation}`
  → `use harness::pipeline::{Fixability, Violation}` — конверсійна логіка не
  змінюється.

### 2.8 Тести `rules-fix`

Усі наявні тести, що будують `RungTier`/`Rung`/`AttemptContext` вручну
(`attempt.rs::tests`), потребують:
- `use harness::ladder::{Rung, RungTier};` замість `llm_lib::fix::ladder::…`;
- `AttemptContext` тепер вимагає поле `journal: Arc<Mutex<llm_lib::journal::Journal>>`
  — додай `journal: Arc::new(Mutex::new(llm_lib::journal::Journal::new()))` у
  тестові фікстури; і поле `has_next_rung: bool` — постав `true`/`false`
  за смислом тесту.
- Нові поля `FixRequest` (`rung`, `output_ceiling`, `tool_result_ceiling`,
  `context`, `has_next_rung`, `ttft_calibration`) — заповни тестовими
  значеннями там, де тести напряму будують `FixRequest`.

## 3. `crates/rules-cli/src/fix_cmd.rs`

Імпорти переїжджають з `llm_lib::fix::…` у `harness::…`:
```rust
use harness::ladder::{RungCapBudget, DEFAULT_MAX_AVG};
use harness::pipeline::{FixReport, PipelineOutcome};
```
(`RungFailure` теж у `harness::pipeline`.) `Cargo.toml` `crates/rules-cli/Cargo.toml`:
прибери пряму залежність на `n7n-llm-lib` (`fix_cmd.rs` після переїзду вже
нічого з `llm_lib::` напряму не бере — перевір `grep -n "llm_lib::" crates/rules-cli/src/`,
щоб не лишити мертвого імпорту), додай:
```toml
harness = { version = "0.1", package = "n7n-harness" }
```

Перейменування у самому `fix_cmd.rs`:
- `AvgBudget::new(DEFAULT_MAX_AVG)` → `RungCapBudget::new()` (конструктор
  без параметрів тепер капує І `cloud-avg`, І `cloud-max` — розділ 2.5;
  `DEFAULT_MAX_AVG`-імпорт можна прибрати, якщо більше ніде не читається).
- `report.avg_cap_skipped` → `report.cap_skipped`.
- `RungFailure::AvgCapExhausted` → `RungFailure::CapExhausted`.

Решта файлу (`concern_keys`, `exit_code`, `describe_failure`, рендер
звіту) логічно не змінюється — лише типи полів, на які він посилається.

## Порядок роботи і перевірка

1. **rules-core** (розділ 1) — найменший блокер компіляції, зроби першим і
   переконайся, що `cargo build -p rules-core` (чи як тут зветься crate)
   проходить.
2. **rules-fix** (розділ 2) — основна маса роботи. Рекомендований підпорядок:
   Cargo.toml → import-перейменування (2.2, 2.7) без зміни логіки → `t0.rs`
   (2.3, найскладніший дизайн — почни з дослідження `NATIVE_FIXES`,
   розділ 2.3) → `attempt.rs` (2.4) → `config.rs` (2.6) → `lib.rs` (2.5) →
   тести (2.8).
3. **rules-cli** (розділ 3) — тривіальний після того, як `rules-fix`
   компілюється.
4. Після кожного кроку — `cargo test` відповідного крейта. Наскрізний
   `cargo test --workspace` наприкінці.
5. **НЕ комітити й не пушити** — залиш зміни в робочій директорії; коміт і
   PR — окреме рішення користувача (як і з попередньою міграцією `n7n-g`).
6. У фінальному звіті: список змінених файлів, стан кожного пункту
   (зроблено/не застосовно/потребує рішення користувача — особливо пункт
   2.3 «перезапис наявного файлу через T0» і пункт 2.6 «`meta.cloud_timeout_ms`»,
   якщо реальний код розійшовся з рекомендацією цього промту), результати
   тестів, і окремо — усе, де довелось відступити від цього промту, бо
   реальний код `llm-lib`/`harness` виявився іншим (промт писаний проти
   стану коду на 2026-08-19, звіряй самостійно).
