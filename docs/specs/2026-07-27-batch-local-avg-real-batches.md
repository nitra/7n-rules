# Batch-запити до LOCAL AVG: міст до справжнього /v1/batches і хвильова оркестрація

**Дата:** 2026-07-27
**Статус:** погоджено — готово до реалізації
**Зв'язані документи:** `docs/specs/2026-07-24-batch-emulation-bench.md` (2b-емуляція, T8), `docs/specs/2026-07-23-llm-cascade-single-source-spec.md` (тир-каскад), PR #249 (litellm як другий local-провайдер), k8s-репо: `llm-d/readme.MD`, `batch-adapter/adapter.mjs`

## 1. Проблема / Мета

Оркестратори скілів (насамперед doc-files) роблять LLM-запити до локальної моделі
послідовно або через клієнтську 2b-емуляцію batch-у (`@7n/llm-lib/batch` →
чанкований конкурентний прогін у Rust-крейті). Водночас у k8s вже розгорнуто
**справжній** OpenAI-сумісний Batch API: сервіс `batch-adapter` (`POST /v1/files`,
`POST /v1/batches`, poll, `GET /v1/files/{id}/content`) поверх Valkey-черги та
llm-d (vLLM, `gemma-4-26B-A4B-it-AWQ-4bit`, KEDA scale-to-zero, максимум 1
GPU-нода). Клієнтський бік про нього не знає.

Мета: коли активний LOCAL AVG (зараз — gemma-4 26b через litellm), оркестратор
готує всі запити прогону (напр. 10 файлів doc-files) і відправляє їх **одним
batch-ом** через справжній `/v1/batches`, з фолбеком на наявну емуляцію. Драйвери
(зафіксовані на сесії): швидкість wall-clock, уніфікація для всіх LLM-споживачів
репо, перехід зі "здається batch" на справжній Batch API.

Обмеження:

- Серверний бік живе в окремому репо (k8s); фікси адаптера — окремі PR там.
- KEDA cold-start: перший запит після idle чекає підйому GPU-ноди (Spot L4 → A100).
- `maxReplicaCount: 1` — конкурентність обмежена одним vLLM-подом; справжній
  виграш batch-у — server-side continuous batching, не паралельні ноди.
- Zero-native споживачі (без napi-аддона) мають лишатися працездатними
  (послідовний фолбек), як у T8.

## 3. Деталі реалізації

### Фаза 1 — міст до справжнього Batch API + уніфікація

**Rust-крейт `llm_lib::batch` (+ napi):**

1. Новий backend `openai-batches` поруч із наявною емуляцією:
   `upload JSONL (/v1/files, purpose=batch)` → `POST /v1/batches` →
   poll `GET /v1/batches/{id}` (мапити `request_counts.completed` →
   наявний `onProgress`) → `GET /v1/files/{output_file_id}/content` →
   розпарсити JSONL у ті самі `BatchResult[]` (порядок вхідних items,
   `customId` збережено).
2. Capability-детект з кешем на процес: проба batch-ендпоінта для
   base URL провайдера (404/ECONNREFUSED → емуляція). Явний override
   через опцію (`backend: 'emulated' | 'openai-batches' | 'auto'`,
   дефолт `auto`) — для тестів і діагностики.
3. Тир-правило (рішення Б): `auto` обирає `openai-batches` лише коли
   провайдер model-spec — litellm; інакше емуляція. Мапу
   `localProviders` не міняти — batch-URL деривується з `baseUrl`
   litellm-провайдера (адаптер автентифікує той самий virtual key через
   litellm `/v1/models`).
4. Помилки: per-item `error` з output JSONL мапиться в `BatchResult.error`
   (класифікація на боці споживача не змінюється — `classifyDocgenError`
   вже це вміє); фейл усього batch-у (`status: failed`) → виняток з
   повідомленням із `errors[]` адаптера.
5. Durable-поведінка: `batch_id` логувати у chain/trace; при обриві
   клієнта повторний прогін дозволено (нова генерація), а результати
   попереднього batch-у лишаються на PVC адаптера — окремого
   resume-механізму у фазі 1 не будуємо (зафіксовано як відкрите
   питання).

**JS-шар (`llm-lib/lib/batch.mjs`):** без зміни сигнатури; прокинути
`backend` в опції; JSDoc-оновлення (це вже не «лише емуляція»).

**doc-files (`docgen-files-batch/main.mjs`):** зміни мінімальні —
`runBatchPass` вже готує items і кличе `submitBatch`; додати:

- warmup-ping (рішення Е) на старті `prepareBatchTargets`, лише коли
  детект показав `openai-batches` (fire-and-forget, помилку ігнорувати);
- прокидання тиру/spec від оркестратора (рішення Б) — сьогодні модель
  вже передається, лишилося не «вгадувати» batch-доступність порожнім
  `submitBatch('min', [])`, а питати нового capability-API.

**Уніфікація споживачів (кластер E):** перевести на `submitBatch`
накопичувані незалежні промпти:

- `npm/scripts/lib/adr/normalize-pipeline.mjs` — батч чернеток ADR;
- `npm/rules/test/coverage/lib/llm.mjs` — LLM-аналіз покриття;
- `npm/rules/text/cspell-fix/fix-worker.mjs` — виправлення typo.

Вимога до API з цього кластера: жодних doc-files-специфічних полів у
`BatchItem`/`BatchResult` (сьогодні їх і немає — тримати так).

**batch-adapter (k8s-репо, окремий PR):**

- per-item параметри: слати кожен item окремим `/v1/chat/completions`
  з його власними `max_tokens`/`temperature`, конкурентність =
  `BATCH_SIZE` (llm-d/vLLM батчить server-side автоматично);
- прибрати нестандартний один-POST `messages: chunk.map(...)`;
- опційно: динамічний розмір чанка за сумою оцінених токенів.

**Акцепт-критерій фази 1:** `doc-files gen` на наборі з ≥10 файлів при
активній LOCAL AVG проходить одним `/v1/batches`-job-ом; результати
per-item ідентичні за якістю одиночним викликам (per-item `max_tokens`
шановано); wall-clock суттєво менший за послідовний прогін; при
недоступному адаптері прогін автоматично йде емуляцією без зміни CLI.

### Фаза 2 — хвильова оркестрація (власний акцепт-критерій)

Зняти компроміс T8 (batch = one-shot): повний конвеєр якості
(секції → critique → refine → best-of-2 → judge) виконувати
**хвилями батчів по всіх файлах**, а не per-file послідовно:

1. Хвиля 1: незалежні секційні промпти всіх файлів одним batch-ом.
2. Хвиля 2: critique-промпти всіх секцій, що цього потребують.
3. Хвиля 3: refine лише там, де критик не сказав NONE.
4. Хвиля 4 (опц., `N_CURSOR_DOCGEN_JUDGE=1`): judge усіх зібраних доків;
   degraded доретраюється в межах того ж прогону (ідея №13 сесії).

Стан між хвилями (facts/anchors/intent/mode кожного файлу) тримає
JS-оркестратор у пам'яті процесу — це розширення `prepareBatchItem` →
`prepare*Wave*Items`, DAG не персистується. Best-of-2 — друга гілка
хвилі 1 з temperature 0.5 лише для файлів зі score < порога після
det-скорингу.

**Акцепт-критерій фази 2:** розподіл score/degraded на бенч-наборі
(як у `2026-07-24-batch-emulation-bench.md`) не гірший за послідовний
шлях, wall-clock — кратно менший; judge працює в batch-шляху.

## Відкриті питання

- **Resume після падіння клієнта:** результати завершеного batch-у лежать
  на PVC адаптера; чи потрібен клієнтський `--resume batch_id` (перечитати
  готовий output без повторної генерації) — вирішити після експлуатації фази 1.
- **Completion window / нічні прогони:** адаптер декларує `24h`; сценарій
  «сабмітнув увечері — забрав уранці» (ідеї №14/№29/№43) свідомо не
  специфікований — окрема сесія, якщо зʼявиться потреба.
- **`POST /cancel` для deadline-рунгів:** знімає єдину причину примусово
  послідовних fix-pipeline рунгів (ідея №41) — кандидат у фазу 2+, потребує
  узгодження семантики часткових результатів скасованого batch-у.
- **Масштабування >1 GPU:** KEDA-скейл за довжиною Valkey-черги і
  multi-worker адаптера (ідеї №6/№23) — k8s-бік, поза цією спекою.
