# Серіалізований plugin contract v3 — wasm-компонент як єдина форма плагіна

**Дата:** 2026-07-31
**Статус:** погоджено — готово до реалізації (усі відкриті питання першої
редакції закрито ітеративним раундом 2026-07-31 → рішення К–О)
**Зв'язані документи:** `docs/specs/2026-07-30-rules-v2-rust-core-migration.md` (§7 —
плагінні концерни заблоковані «до окремого рішення про крос-пакетний контракт»; цей
документ і є тим рішенням), `docs/specs/2026-07-27-universal-plugin-slots-lang-php-extraction.md`,
`docs/specs/2026-07-18-lang-plugins-extraction-spec.md`.

## 1. Проблема / Мета

Plugin API v2 — це JS-контракт: маніфест `package.json → "n-rules".contributes`,
обробники — mjs-модулі, які оркестратор завантажує через `import()`. Поки контракт
живе на рівні JS-модулів, оркестратор зобов'язаний бути JS-процесом — це блокує
дві цілі міграції на Rust core:

1. міграцію плагінних концернів у native (фаза 5 спеки 2026-07-30 явно зупинена
   на цьому рішенні);
2. інверсію entrypoint — `@7n/rules` як Rust CLI, де JS не є обов'язковим runtime.

Обмеження, зафіксовані на brainstorming-сесії (2026-07-31):

- **плагін ≠ npm-пакет** — форма дистрибуції не прив'язана до npm;
- **плагіни не залежать від node** — контракт node-free із дня один;
- **одна канонічна форма плагіна** — без зоопарку «declarative/wasm/binary/builtin»;
- **платформи: macOS / Linux / Windows** — без пер-плагінної матриці native-збірок;
- **LLM-прозорість — першокласний критерій**: створення плагіна автоматизується
  скілом, тож пайплайн має бути детермінованим і повністю описуваним текстом.

## 2. Ухвалені рішення

| # | Питання | Рішення |
|---|---|---|
| А | Форма плагіна | **Wasm-компонент (Component Model), контракт описано WIT.** Один платформо-незалежний артефакт закриває matrix-проблему, sandbox з коробки закриває довіру поза npm. Фасилітатор рекомендував stdio JSON-RPC (зрілість технології, дешевший міграційний міст, простіший host); обрано wasm через sandbox, один крос-платформний артефакт і відповідність напрямку індустрії — ризики зрілості приймаються свідомо, мітигації в §3.6. |
| Б | Сумісність із Plugin API v2 | **Чистий брейк (v3).** Усі плагіни живуть в одному репо — атомарний перехід реальний. `PLUGIN_API_VERSION = 2` і `import()`-диспатч виводяться після завершення міграції; грейс-періоду співіснування немає. |
| В | Міграція чинних JS-плагінів | **Переписування, без ComponentizeJS-моста.** Порядок за формою логіки: декларативні концерни → tool-wrapper-и → динамічні. LLM-скіл (рішення І) використовується і для переписування. |
| Г | Виконання | Embedded **wasmtime** (пінована версія) всередині CLI/napi-аддона. Контракт **синхронний, batch-модель**: один виклик на концерн на прогін (список файлів + вміст → список діагностик). Стрімінг/async свідомо поза v3.0 (WASI 0.3 async сирий); прогрес — на боці хоста, per-concern. Пул інстансів — переюз між викликами. |
| Д | Зовнішні тули | **Host-mediated spawn:** плагін декларує в маніфесті `tools = ["shellcheck@^0.9"]`; хост забезпечує наявність (ensure-tool контур), виконує і повертає вивід через host function. Плагін сам не спавнить нічого (wasm і не може — це перетворює обмеження на перевагу безпеки). Node-тули (ESLint) — та сама механіка: node стає задекларованою tool-залежністю плагіна для JS-репо, де він і так є, а не залежністю контракту. |
| Е | Capabilities | Маніфест декларує повний перелік: `fs-read` scope (→ WASI preopens: плагін фізично бачить лише передані шляхи), `tools`, `network` (за замовчуванням заборонено). Enforcement — хостом із v3.0, бо wasm робить його безкоштовним. |
| Ж | Дистрибуція | **Registry-агностична: пін `url + sha256` у конфігу споживача.** Джерело байдуже — GitHub Releases, OCI (ORAS), npm як один із транспортів, локальний шлях для dev-петлі. Модель довіри: hash-пін (+ місце під sigstore пізніше). **Курованого індексу у v3.0 немає** (рішення Н). |
| З | Схема і версіонування | **WIT — єдине джерело типів контракту.** Версія контракту = версія WIT world (продовження `CONTRACT_VERSION` diagnostics DTO). Negotiation у handshake зі **skip-not-crash** семантикою (як `requiresPluginApi` у v2): несумісний плагін пропускається з попередженням, не валить прогін. Еволюція — additive-only у межах мажорної версії world. |
| И | Builtin-концерни | **Dogfooding:** core-концерни `rules-core` і зовнішні wasm-плагіни реалізують один інтерфейс (Rust trait ↔ WIT host binding). В оркестраторі один кодовий шлях; builtin-и — статично злінковані «плагіни». Чинний реєстр `NATIVE_CONCERNS` узагальнюється до цього інтерфейсу. |
| І | Авторинг | **LLM-скіл створення плагіна — обов'язковий deliverable фази**, нарівні з host-ом. Guest-мова за замовчуванням — Rust (`cargo component build`, найзріліший wasm-toolchain); контракт приймає будь-який компонент, що відповідає WIT. Скіл покриває scaffold → build → golden-тести → publish (артефакт + обчислення sha256 для піна). |
| К | Провайдери поза lint (taze, doc-files) | **Один world `plugin` з усіма інтерфейсами** (concerns, ecosystem, docgen). Плагін декларує підтримувані домени у `describe()` і маніфесті; непідтримані експорти — заглушки `not-supported`, які хост ніколи не кличе (знає з `describe()`). Одна форма артефакта збережена, узгоджено з capability negotiation і skip-not-crash. |
| Л | Слот-payload-и (`ci.artifact@1`) | **Повна WIT-типізація** — кожен слот як типований `record`. Щоб еволюція слота не тягла за собою bump world (мінус, який фасилітатор підняв), типи слотів живуть **в окремому WIT-пакеті** `n-rules:slots@X.Y.Z`, який world імпортує: незалежні цикли версіонування збережено, compile-time безпека в guest-коді є. Семантичні перевірки (safe-path, id-regex зі `slot-contracts-ci.mjs`) переїжджають у host-валідатори `rules-contract` — типів WIT для них замало. |
| М | Каданс піна wasmtime | **Кожен мінор через звичайний taze-флоу**, як решта залежностей; contract-test-kit — гейт від регресій. Свідомий вибір «свіжий Component Model ціною регулярного тертя»; вузький trait у `rules-plugin-host` (§3.1) локалізує правки при API-змінах. |
| Н | Курований індекс плагінів | **У v3.0 не вводиться.** Споживач пінить `url + sha256` напряму. Щоб це не було UX-тертям, CLI шипить **вбудовані дефолтні піни first-party плагінів** (той самий lockstep-механізм, що синхронізує platform-пакети) — ручні піни потрібні лише для власних/сторонніх плагінів. Індекс — природне узагальнення цих дефолтів, коли парк плагінів виросте. |
| О | Windows | **win-x64 додається у platform-матрицю до релізу v3.0**, у рамках цієї ж фази (заодно кандидат — linux-arm64-gnu). Інакше «підтримуємо Windows» неправда: плагіни крос-платформні, а хоста немає. Обсяг: рядки в `npm-publish.yml`, windows-гілка в loader-і (`.dll`), і windows-специфічні тести (роздільники шляхів, CRLF, спавн тулів). |

## 3. Деталі реалізації

### 3.1. Крейти і артефакти

- `crates/rules-contract` — WIT-визначення (`wit/`), serde-DTO, JSON Schema
  (schemars) для маніфеста; єдине джерело типів для host-а, builtin-концернів
  і guest-байндингів.
- `crates/rules-plugin-host` — обгортка wasmtime: завантаження компонента,
  преконфігурація WASI (preopens за capabilities), host functions, пул
  інстансів, negotiation. Вузький публічний trait — wasmtime за ним інкапсульований
  (мітигація API-churn).
- Плагін = один `.wasm` + `plugin.toml` (маніфест): id, версія, версія world,
  контрибуції (concerns, slots, providers), capabilities, tools.

### 3.2. Ескіз WIT world (v3.0)

```wit
package n-rules:plugin@3.0.0;

// типи слотів — окремий пакет із власним циклом версіонування (рішення Л)
use n-rules:slots/ci-artifact@1.0.0;

world plugin {
  // host → plugin: describe() декларує підтримувані домени (рішення К)
  export describe: func() -> manifest;

  // lint-домен
  export detect: func(batch: detect-batch) -> list<diagnostic>;
  export fix: func(request: fix-request) -> fix-plan;

  // інші домени — заглушки not-supported, якщо не задекларовані в describe()
  export ecosystem-outdated: func(request: ecosystem-request) -> domain-result<list<outdated-dep>>;
  export docgen-render: func(request: docgen-request) -> domain-result<doc-output>;

  // plugin → host
  import report-progress: func(done: u32, total: u32);
  import run-tool: func(tool: string, args: list<string>, stdin: option<string>) -> tool-output;
  import log: func(level: log-level, message: string);
}
```

`diagnostic` віддзеркалює чинний diagnostics DTO (`CONTRACT_VERSION = 2`,
`crates/rules-core/src/dto.rs`) — v3 успадковує форму, не вигадує нову.
Вміст файлів хост передає у `detect-batch` (він уже читав їх для scan) — плагін
не робить повторний IO і не потребує fs-capability для типового концерну.

### 3.3. Оркестрація

- Диспатч-гілка в `runConcernDetector` (зараз: `NATIVE_CONCERNS` → native, інакше
  `import(main.mjs)`) стає єдиною: реєстр концернів = builtin (static) + wasm
  (з resolved-плагінів). Гілка `import()` зникає з виведенням v2.
- Резолв плагінів: конфіг споживача (`.n-rules.json`) отримує секцію
  `plugins: [{ name, url, sha256 }]`; завантаження — у локальний кеш
  (`~/.cache/n-rules/plugins/<sha256>.wasm`), верифікація hash перед першим
  завантаженням у host. Чинний plugin-resolve кеш замінюється цим контуром.
- Slot-контракти (`ci.artifact@1` тощо) — типовані records у WIT-пакеті
  `n-rules:slots` (рішення Л); семантичні перевірки з `slot-contracts-ci.mjs`
  (safe-path, id-regex) стають host-валідаторами в `rules-contract`. JS re-export
  із `plugin-api.mjs` виводиться разом із v2.
- Домени поза lint (рішення К): хост читає `describe()` один раз при завантаженні
  плагіна, будує мапу «домен → чи підтримано» і не викликає незадекларовані
  експорти. Заглушка повертає `domain-result::not-supported` — захист від
  розсинхрону маніфеста й реалізації, не основний шлях.

### 3.4. Дистрибуція

- Пін у конфігу споживача: `plugins: [{ name, url, sha256 }]`. Транспорти —
  GitHub Releases (первинний для власних плагінів), npm/OCI — опційні дзеркала.
  Для dev-петлі — `file:`-url без hash-перевірки (лише поза CI).
- **First-party піни вбудовані в CLI** (рішення Н): дефолтна таблиця
  `name → url + sha256` для власних плагінів синхронізується тим самим
  lockstep-кроком у `npm-publish.yml`, що вже синхронізує platform-пакети;
  споживач перевизначає пін лише за потреби. Mirror-тест консистентності —
  за зразком `native-packages.test.mjs`.
- Курованого індексу немає у v3.0; коли парк виросте, він вводиться як
  узагальнення вбудованої таблиці, без зміни формату піна.

### 3.4a. Платформна матриця (передумова релізу v3.0)

`npm-publish.yml` розширюється на **win-x64** (кандидат заодно —
linux-arm64-gnu) до релізу v3.0 (рішення О): без хоста під Windows
крос-платформність плагінів не має сенсу. Обсяг: рядки матриці, windows-гілка
в `native.mjs` (`.dll`), windows-специфічні тести — роздільники шляхів у
DTO-контракті, CRLF у діагностиках і range-ах, `run-tool` спавн.

### 3.5. Порядок робіт

1. `rules-contract` (WIT world + пакет `n-rules:slots` + host-валідатори) +
   `rules-plugin-host` + negotiation + golden-фікстурний contract-test-kit
   (та сама parity-механіка, що у фазі 1 міграції).
2. Пілот: один декларативний концерн із чинного плагіна переписується як
   wasm-компонент, проганяється через host у реальному lint-прогоні.
3. LLM-скіл авторингу (scaffold/build/test/publish) — верифікується тим, що
   наступний плагін створюється лише через нього.
4. Розширення platform-матриці на win-x64 (§3.4a) — може йти паралельно з 1–3,
   але має завершитись до кроку 6.
5. Переписування решти: декларативні → tool-wrapper-и (`run-tool` контур) →
   динамічні (lang-js провайдери — останні); домени taze/doc-files — у тому ж
   world (рішення К), тож без окремої фази.
6. Виведення Plugin API v2: видалення `import()`-диспатчу, `plugin-api.mjs`
   деградує до re-export типів/схем для legacy-споживачів документації; мажорний
   реліз `@7n/rules` (збігається з запланованим мажором платформної межі).

### 3.6. Мітигації ризиків wasm-рішення

| Ризик | Мітигація |
|---|---|
| Component Model churn (wasmtime ламає API) | Весь wasmtime-код за вузьким trait-ом `rules-plugin-host`; пін рухається кожен мінор через taze-флоу (рішення М) з обов'язковим прогоном contract-test-kit — тертя регулярне й мале замість рідкісного й великого |
| Async/стрімінг сирі у WASI | Синхронний batch-контракт v3.0 (рішення Г); стрімінг — кандидат на v3.x, коли WASI 0.3 стабілізується |
| Переписування JS-плагінів на критичному шляху | Порядок §3.5.5 виносить найважче в кінець; скіл знижує вартість кожного наступного; ComponentizeJS свідомо відкинуто (рішення В) — не тримаємо другий toolchain |
| LLM-скіл деградує разом із toolchain-ом | Скіл пінить версії (`cargo-component`, wit-bindgen) і має власний smoke-тест у CI (scaffold → build → detect на фікстурі) |
| Розмір/швидкість wasm-артефактів | Пул інстансів (рішення Г), release-профіль із `opt-level = "s"`, бюджет розміру в contract-test-kit |

## Відкриті питання

П'ять питань, відкритих у першій редакції спеки, закрито ітеративним раундом
2026-07-31 — вони стали рішеннями К, Л, М, Н, О. Лишається:

- **sigstore/cosign-підпис артефактів** — модель довіри v3.0 стоїть на hash-піні;
  підпис — кандидат на v3.x, рішення відкладено до появи сторонніх авторів.
- **Бюджет розміру wasm-артефакту** — конкретна межа для gate у contract-test-kit
  визначається на пілоті (§3.5.2), коли з'явиться перший реальний компонент.
- **Доля `fix`-контуру для не-мігрованих концернів** під час кроку §3.5.5 —
  чи всі fix-и переїжджають разом із detect-ом свого концерну (очікувано так),
  чи є концерни зі спільними fix-хелперами, які потребують окремого порядку.
