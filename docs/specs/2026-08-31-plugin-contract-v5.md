# Контракт `n-rules:plugin@5.0.0` — повноваження як світи

**Дата:** 2026-08-31
**Статус:** погоджено — готово до реалізації
**Зв'язані:**
`2026-08-30-contract-roadmap-blocked-concerns.md` (рішення 1–5),
`2026-08-31-slice6-consumer-surfaces.md` (рішення 6–11),
`2026-07-31-plugin-contract-v3-wasm-component.md` (рішення Л — окремий пакет слотів),
`docs/plans/2026-08-31-full-rust-migration-plan.md`.

## 1. Мета

Мажор `4.0.0` розблокував бінарну родину `image-*`, додавши `write-bytes`.
Мажор `5.0.0` розвʼязує інший клас: **сьогодні кожна нова поверхня коштує
зміну контракту**, і це робить будь-яке розширення платним назавжди.

`world.wit:105-111` формулює обмеження точно: без width-subtyping будь-яка
зміна форми межі — мажор, і безкоштовна лише адитивна еволюція
`import`/`export`/`resource`. Отже мета `5.0.0` — не «додати ще одну
поверхню», а **зробити наступну поверхню безкоштовною**.

Це досягається одним рухом: тип поверхні виноситься з форми ядрового світу.

## 2. Що не так із поточною формою

### 2.1. Повноваження оголошуються, а не типізуються

Ядровий світ несе пʼять імпортів (`report-progress`, `run-tool`,
`exec-tool`, `log`, `host-context`), і **всі вони належать кожному гостю за
типом**. Обмежує їх `plugin.toml`: `tools` каже, які інструменти дозволені,
`capabilities.fs-read` — які шляхи, `capabilities.network` — чи потрібна
мережа.

Гейт стоїть **збоку від системи типів**. Гість, який ніколи не мав
запускати процеси, все одно має `run-tool` у своєму типі; заборона тримається
на тому, що хост звірить декларацію.

**Заміряно 2026-08-31:** усі шість гостей оголошують `fs_read = []` і
`network = false`. Тобто декларативний гейт, який ми маємо, **порожній
скрізь** — він не перевіряє нічого реального, лише існує.

### 2.2. Слотова поверхня не має способу бути оголошеною

Три доведені споживачі чекають на канал, якого немає:

| хто | що потрібно | джерело |
|---|---|---|
| `coverage-provider` × 4 плагіни (31 файл) | слот `coverage` — у контракті відсутній | розвідка `2026-08-31-recon-providers-rules-skills.md` |
| `rules-docs docs build` | мовні екстрактори через slot-dispatch | `crates/rules-docs/src/lib.rs:30-33` |
| `docgen` як гість (рішення 1) | те саме | рішення 1 |

Плюс дві напівживі поверхні: `ecosystem-outdated` і `docgen-render` у
контракті **є**, але всі шість гостей віддають `NotSupported` — форма
оголошена, механізм не добудований.

### 2.3. Прецедент, на який спираємось

Пакет `n-rules:slots@1.0.0` (`wit/deps/slots/ci-artifact.wit`) **уже існує
окремо**, з власним циклом версіонування — рішення Л контракту v3: «еволюція
слоту (`ci.artifact@2` тощо) не тягне за собою bump plugin-world».

Тобто напрямок закладений ще в v3; `5.0.0` доводить його до кінця.

## 3. Нова структура пакетів

```
wit/
  world.wit                      package n-rules:plugin@5.0.0     ядровий світ
  deps/
    slots/ci-artifact.wit        package n-rules:slots@1.0.0      (без змін)
    caps/
      tool-runner.wit            package n-rules:caps@1.0.0       світи повноважень
      file-reader.wit
      llm-consumer.wit
    surfaces/
      coverage-provider.wit      package n-rules:surfaces@1.0.0   слотові світи
      knowledge-extractor.wit
      docgen-stage.wit
```

Три родини, три цикли версіонування. Ядро змінюється рідко; повноваження й
поверхні ростуть незалежно.

## 4. Принцип гранулярності

Світ = **клас повноважень**, не функція. Поверхня стає окремим світом, якщо
виконується хоч один критерій:

1. дає доступ до ресурсу поза межами переданих даних (диск, процеси, мережа,
   модель);
2. має ненульову зовнішню ціну (гроші, час стороннього сервісу);
3. є слотовою поверхнею, тобто її реалізує підмножина гостей.

За цим критерієм:

- `log` і `report-progress` **лишаються в ядрі** — не дають доступу нікуди й
  потрібні всім;
- `run-tool` + `exec-tool` — **один світ**, не два: це один клас повноважень;
- `host-context` лишається в ядрі — він віддає рядок зі скоупу, який хост
  сам і визначив.

## 5. Ядровий світ після `5.0.0`

```wit
package n-rules:plugin@5.0.0;

world plugin {
  use n-rules:slots/ci-artifact@1.0.0.{descriptor as ci-artifact-descriptor};

  // … типи без змін: severity, concern-scope, diagnostic, source-file,
  // detect-batch, fix-request, fix-plan, file-edit …

  import report-progress: func(done: u32, total: u32);
  import log: func(level: log-level, message: string);
  import host-context: func(slot: string) -> option<string>;

  export describe: func() -> manifest;
  export detect: func(batch: detect-batch) -> list<diagnostic>;
  export fix: func(request: fix-request) -> fix-plan;
}
```

Із ядра **виходять** `run-tool`, `exec-tool` (у `caps:tool-runner`) і
напівживі `ecosystem-outdated`/`docgen-render` (у відповідні слотові світи).

## 6. Світи повноважень

### 6.1. `n-rules:caps/tool-runner`

```wit
world tool-runner {
  import run-tool: func(tool: string, args: list<string>,
                        stdin: option<string>) -> tool-output;
  import exec-tool: func(request: tool-request) -> tool-result;
}
```

Гість, що не оголосив цей світ, **не має цих імпортів у своєму типі** — не
«дістає відмову в рантаймі».

### 6.2. `n-rules:caps/file-reader` — рішення 2

```wit
world file-reader {
  /// Перелік шляхів за глобами, БЕЗ вмісту. Дає гостю дізнатись обсяг
  /// перед тим, як платити за читання.
  import list-files: func(globs: list<string>) -> list<string>;

  /// Вміст одного файлу БАЙТАМИ. `list<u8>`, не `string`: бінарні файли
  /// перестають ламатись, і зникає клас вад `from_utf8_lossy` (§2.83).
  import read-file-bytes: func(path: string) -> result<list<u8>, domain-error>;
}
```

**Що це знімає.** §2.92 тримала `bun/package_json` непортовним із двох
причин, і `file-reader` знімає обидві: тип межі (`list<u8>` замість
`string`) і обсяг (гість читає вибірково, а не дістає 124 MiB на виклик при
~1 MiB корисного).

Хост і далі відповідає за скоуп: `list-files` не виходить за корінь репо й
поважає `.n-rules.json:ignore` (той самий обхід, що `build_full_scope_files`).

### 6.3. `n-rules:caps/llm-consumer`

```wit
world llm-consumer {
  import llm-call: func(request: llm-request) -> result<llm-response, domain-error>;
}
```

Виклик робить **хост**: ключі не покидають хост, гість не бачить
креденшелів. Прецедент — `run-tool`: гість просить, хост вирішує.

## 7. Слотові світи

```wit
world coverage-provider {
  export collect-coverage: func(request: coverage-request)
    -> result<coverage-report, domain-error>;
}

world knowledge-extractor {
  export extract: func(request: extract-request)
    -> result<knowledge-candidate, domain-error>;
}

world docgen-stage {
  export run-stage: func(request: stage-request)
    -> result<stage-output, domain-error>;
}
```

Нова слотова поверхня = **новий світ у пакеті `surfaces`**, нуль змін
наявного. Гості, що її не реалізують, не зачеплені.

## 8. Дискавері: маніфест у custom section, без інстанціації

**Проблема курки й яйця:** щоб знати, які світи реалізує компонент, треба
прочитати маніфест; щоб прочитати маніфест, треба викликати `describe()`;
щоб викликати `describe()`, треба вже проінстанціювати проти правильного
набору імпортів.

**Розвʼязання вже збудоване.** Робота Д2 вбудовує маніфест у **custom
section** компонента (`oci-dist-package::embed_manifest`, секція
`nitra.plugin-manifest/v1`). Хост читає перелік світів **із байтів файлу, до
будь-якої інстанціації** — `inspect_component`, без wasmtime.

Тобто дискавері не потребує окремого механізму: він падає з дистрибуції,
яку ми й так робимо.

### Поле маніфесту

```wit
record manifest {
  // … наявні поля без змін …

  /// Світи повноважень і слотові світи, які цей компонент реалізує, у формі
  /// `namespace:package/world@version` (напр. `n-rules:caps/tool-runner@1.0.0`).
  /// Ядровий світ `n-rules:plugin` не перелічується — його реалізують усі.
  worlds: list<string>,
}
```

Це **єдина зміна форми** в маніфесті, і саме вона робить мажор неминучим:
нове поле в record → `expected record of N fields, found N-1`.

## 9. Хост: лінкер під оголошені світи

Замість одного статичного лінкера — побудова набору імпортів під перелік із
маніфесту:

1. прочитати custom section → `worlds`;
2. звірити major ядрового світу (наявний `check_world_version`);
3. відхилити гучно невідомий світ — не ігнорувати;
4. зібрати лінкер: ядро + по одному модулю на кожен оголошений світ;
5. інстанціювати.

**Тут житиме нова складність**, і це названо чесно: сьогодні лінкер один і
статичний.

### Що лишається від `capabilities`

Два рівні, що відповідають на різні питання:

| рівень | питання | де живе |
|---|---|---|
| світ | чи взагалі може | тип компонента |
| декларація | які саме шляхи/інструменти | `plugin.toml` |

`capabilities.fs-read` лишається як звуження для `file-reader`;
`capabilities.network` — кандидат на видалення (зміряно: `false` у всіх
шести, а мережеві дії йдуть через хост).

## 10. Міграція шести гостей

Мажор ламає всіх одномоментно (`check_world_version` не вантажить `4.x` на
`5.x`), тож міграція одна хвиля:

| гість | оголошує |
|---|---|
| `lang-js` | `tool-runner` |
| `lang-python`, `lang-rust`, `lang-php` | `tool-runner` |
| `ci-github`, `ci-azure` | `tool-runner` |
| `docgen` (новий, рішення 1) | `file-reader`, `llm-consumer`, `docgen-stage` |
| чотири `coverage-provider` (рішення 3) | `coverage-provider` |

## 10.1. Перехід на WASI 0.3 (`wasm32-wasip3`) — тією самою хвилею

**Рішення 2026-08-31.** Гості переходять із `wasm32-wasip2` на
`wasm32-wasip3` разом із мажором, а не окремо.

### Чому зараз, а не потім

Той самий аргумент, яким обґрунтовано склад мажора: перехід ламає всіх
шістьох гостей і вимагає перезбірки — а мажор `5.0.0` це вже робить.
Зробити окремою хвилею означає перезбирати всіх удруге.

### Що вже готове, а що ні

**`wasmtime` не обмежує.** Обидва проєкти на версії 48; різниця лише у
feature-прапорці:

```
7n-rules:  wasmtime-wasi features = ["p2"]
r-plugin:  wasmtime-wasi features = ["p3"]
```

Тобто хост уміє P3 сьогодні — треба лише перемкнути прапорець.

**Ціль існує в компіляторі, але не роздається.** Зміряно 2026-08-31:

```
rustc --print target-list | grep wasip  →  wasip1, wasip1-threads, wasip2, wasip3
rustup target list        | grep wasip  →  wasip1, wasip1-threads, wasip2 (installed)
```

`wasm32-wasip3` компілятор знає, але precompiled `std` через rustup не
роздається. Отже збірка вимагає `-Z build-std` або WASI SDK.

### Піновані версії (рішення власника 2026-08-31)

| що | версія | примітка |
|---|---|---|
| WASI | **0.3.1** | `github.com/WebAssembly/WASI/releases` |
| WASI SDK | **мінімум `wasi-sdk-34`** | **фінальний реліз**, не `34.0-rc.2` |
| Rust toolchain | пінований у `rust-toolchain.toml` | зараз файлу немає взагалі — заводиться цією хвилею |

**Розбіжність із `r-plugin`, яку треба врахувати при переносі.** Сусідній
проєкт стоїть на `wasi-sdk-34.0-rc.2`, і його скрипт добування перевіряє
SHA-256 архіву та `VERSION`-метадані **саме тієї** збірки. Ми пінимо
фінальний `wasi-sdk-34`, тож скрипт переноситься **за формою, не дослівно**:
контрольні суми й очікуваний `VERSION` інші, і копіювання без перерахунку
дало б гейт, що мовчки пропускає не ту збірку — рівно той клас, який ми
виполюємо.

Мінімум, а не точна версія: `wasi-sdk-34` — нижня межа, новіші мажори SDK
приймаються, старіші відхиляються гучно.

### Референс уже є в сусідньому репозиторії

`nitra/r-plugin` збирає гостей під `wasm32-wasip3` сьогодні: пінований
`nightly-2026-08-27` (`rust-toolchain.toml`) плюс WASI SDK 34.0-rc.2 з
перевіркою SHA-256 архіву й `VERSION`-метаданих перед розпакуванням.

Це головний де-ризикувач рішення: ми не першопрохідці, і робочий взірець
лежить у сусідньому репо тієї ж організації.

### Побічна знахідка: у нас немає `rust-toolchain.toml`

`r-plugin` пінить `nightly-2026-08-27`; **у `7n-rules` файлу немає взагалі**,
і збірка йде тим toolchain-ом, що стоїть на машині — сьогодні це
`1.100.0-nightly (bff8e12ff, 2026-08-26)`.

Тобто ми **вже на nightly, але випадково, а не за рішенням**. Це самостійний
ризик того ж класу, що `KNOWN_PLUGIN_RANGES` (#578): непіноване, доки не
розійдеться. Перехід на P3 робить пінування **обовʼязковим**, а не бажаним —
`-Z build-std` без пінованого каналу невідтворюваний за побудовою.

### Що з `oci-dist`

Крейт `oci-dist-package` до `0.2.0` приймав лише `wasm32-wasip3` — засновку
першого споживача (`r-plugin`), яка блокувала нас (§2.101). Послаблення до
списку відомих профілів лишається правильним і після цього рішення:
транспорт зберігає байти й digest, а сумісність профілю — політика того, хто
активує компонент. Те, що обидва споживачі зійдуться на P3, робить
обмеження непотрібним, а не виправданим.

### Чого P3 нам дає і чого ні

Головне у WASI 0.3 — **нативний async** (streams/futures у Component Model).
`r-plugin` його потребує: він стрімить UI-рендер із гостя.

Наші гості синхронні за формою (`detect(batch) -> list<diagnostic>`,
`fix(request) -> fix-plan`), тож сьогодні async не покращує нічого.
**Але рішення 1 і 4 це змінюють:** `docgen` як гість кличе LLM через
`llm-call`, а виклик моделі довгий і природно стрімовий. Тобто потреба
зʼявляється не «взагалі», а конкретно — і краще мати платформу під неї до
того, як `docgen` почнуть портувати.

## 11. Що входить у мажор

За практикою `4.0.0` (`world.wit:108-111`): мажор платиться один раз і несе
всі накопичені зміни форми разом.

1. Поле `worlds` у `record manifest`.
2. Винесення `run-tool`/`exec-tool` із ядра.
3. Винесення `ecosystem-outdated`/`docgen-render` у слотові світи.
4. Кандидат: видалення `capabilities.network`.
5. Перехід гостей на `wasm32-wasip3` і хоста на `wasmtime-wasi` feature
   `p3` (розділ 10.1), разом із пінуванням toolchain.

Пункти 2–4 самі по собі — зміни форми світу, тобто мажор. Робити їх окремими
релізами означало б ламати шістьох гостей кілька разів замість одного.

## 12. Порядок реалізації

1. Пакети `caps` і `surfaces` з визначеннями світів (WIT, без коду).
2. Поле `worlds` у маніфесті + валідатор (`rules-contract::validators`).
3. Хост: лінкер під оголошені світи + гучна відмова на невідомий світ.
4. Міграція шести гостей на `5.0.0` — одна хвиля.
5. `file-reader` як перший реальний споживач: порт `bun/package_json`.
6. `coverage-provider` як перша слотова поверхня.
7. `docgen` як гість — найбільша одинична робота, після 1-6.

## Відкриті питання

- **Форма `llm-request`/`llm-response`.** Синхронний виклик чи стрімінг;
  як передається вибір моделі. Проєктувати разом із портом `docgen`, коли
  буде видно реальні потреби стадій.
- **Чи лишається `capabilities.network`.** Зміряно `false` у всіх шести; але
  видалення — теж зміна форми, тож або зараз, або ніколи до `6.0.0`.
- **Версіонування світів повноважень.** `caps@1.0.0` як один пакет проти
  окремої версії на кожен світ. Перше простіше, друге дозволяє еволюціонувати
  `file-reader` не чіпаючи `tool-runner`.
