# AST-стратегія для wasm-плагінів lang-js — мінідизайн + спайк

**Дата:** 2026-08-01
**Статус:** погоджено — готово до реалізації (спайк підтверджує гіпотезу)
**Зв'язані документи:** `docs/specs/2026-07-31-plugin-contract-v3-wasm-component.md`
(§3.5 п.5 — «lang-js провайдери — останні»; §3.6 — бюджет розміру wasm-артефакту
залишено відкритим до першого реального компонента; «Відкриті питання» —
той самий бюджет), `crates/plugin-lang-js/src/lib.rs` (секція «Регекс-наближення
замість повного oxc AST — БЕЗ контрибуції», де-скоуп трьох concern-ів рішенням
оркестратора після звіту батчу 2), PR #347 (regex-апроксимація п'яти concern-ів
відхилена рев'ю — контрибуція вимагає byte-exact parity).

## Проблема

Переписування `lang-js` у native (§3.5.5) заблокувало п'ять concern-ів на
AST-залежності чинних JS-оригіналів, побудованих на **oxc-parser** (справжній
AST, не regex):

| Concern | JS-оригінал | Обсяг |
|---|---|---|
| `js/utils_imports` | напряму на `oxc-parser` | — |
| `test/no-relative-fs-path` | напряму на `oxc-parser` | — |
| `js-bun-db/safety` | `bun-sql-scan.mjs` | 1071 рядків |
| `js-mssql/deps` | `mssql-pool-scan.mjs` | 610 рядків |
| `js-bun-redis/imports` | `redis-imports.mjs` (lib) | — |

Спроба regex-наближення цих п'яти в контрибуції (батч 2) відхилена рев'ю
(PR #347) і задокументована як де-скоуп у `crates/plugin-lang-js/src/lib.rs`:
Rust `regex`-крейт — це regex-двигун (без lookaround/backreference), не
парсер, і «count+reason, не байтова рівність message» дозволяє wasm-виводу
розійтись із JS-каноном на реальних фікстурах — недопустимо для concern-а,
який споживачі трактують як shadowing-заміну живої реалізації. Потрібне
рішення, яке дає byte-exact parity, а не наближення.

## Спайк — факти (S1)

Гіпотеза: `oxc_parser`/`oxc_ast` — Rust-крейти, guest-и теж Rust ⇒ парсер
живе прямо в компоненті (без host-медіації, без іншого двигуна). Перевірено
тимчасовим крейтом поза репо (`oxc-spike`, scratchpad сесії — див. «Спайк-
артефакт» нижче), за зразком `crates/plugin-lang-js` (cdylib, БЕЗ
wit-bindgen/WIT — для виміру збірки/розміру він не потрібен).

### Збірка

`cargo build --target wasm32-wasip2 --release` з залежностями `oxc_parser`,
`oxc_ast`, `oxc_allocator`, `oxc_span` (усі `=0.137.0`) **збирається без
помилок і без додаткових прапорів** — той самий шлях, що чинний
`crates/plugin-lang-js` (`cargo build` для `wasm32-wasip2` видає готовий
Component Model компонент напряму, окремий adapter-крок не потрібен).

### Розмір

| Профіль | `.wasm` (лише парсер, cdylib, без бізнес-логіки) |
|---|---|
| Дефолтний release (без `[profile.release]`-кастомізації — той самий профіль, що зараз використовує кореневий workspace `Cargo.toml`, без `opt-level`/`lto`/`strip`) | 890 140 байт (~869 KB) |
| `opt-level = "z"`, `lto = true`, `strip = true`, `panic = "abort"`, `codegen-units = 1` | 562 358 байт (~549 KB) |

Для порівняння: чинний `plugin_lang_js.wasm` (9 контрибуйованих concern-ів,
`wit-bindgen` + `regex`-крейт, дефолтний профіль без кастомізації) —
**1 500 108 байт (~1,43 MB)**. Сам парсер (без wit-bindgen glue і без
business-логіки жодного concern-а) додає в дефолтному профілі порівнянний
за порядком величини обсяг до бінарника. `docs/specs/2026-07-31-...md` §3.6
уже рекомендує `opt-level = "s"` як мітигацію розміру — спайк показує, що
агресивніший `"z"` + `lto`/`strip`/`panic=abort` дає помітно менший
результат (549 KB проти дефолтних 869 KB лише на самому парсері) без
помилок збірки, тож рекомендація нижче — `"z"`, не `"s"`.

### Версійний мапінг npm ↔ crates.io

`npm/package.json` (корінь репо) і `bun.lock` пінують `oxc-parser: ^0.137.0`
(резолвиться рівно в `0.137.0`). `cargo info oxc_parser@0.137.0` підтверджує
**точну відповідність версії на crates.io** (`oxc_parser` — Rust-крейт, з
якого napi-біндинг `oxc-parser` на npm генерується; той самий репозиторій
`oxc-project/oxc`, той самий тег релізу). Водночас `cargo info oxc_parser`
(без піна) показує **crates.io вже на 0.142.0** — тобто мапінг версій 1:1
існує, але синхронізація не автоматична: npm-пін і Rust-пін можуть розійтись
незалежно (npm-пін оновлюється через `taze`, Rust-пін — вручну/через
Cargo.lock), і саме тому потрібне явне правило пінування (розділ «Рішення»).

### Мікро-parity

Один і той самий JS-сніпет (4 top-level `ImportDeclaration`, 1
`ExportNamedDeclaration` з `source`, 1 `ImportExpression` у виразі — навмисно
змішано, щоб перевірити, що парсер не плутає суміжні конструкції) розпарсено:

- через npm `oxc-parser` (`parseSync`, реальний пакет із `node_modules`
  кореня репо, `--input-type=module` node-скрипт) — **4** `ImportDeclaration`
  на `Program.body`, конкретні спани `[[1,19],[20,50],[51,74],[75,96]]`;
- через спайк-крейт (`cargo test --release`, host-таргет, не wasm) —
  **4** `ImportDeclaration`, той самий підрахунок.

Кількість збігається біт-у-біт. Спани явно не звірялись 1:1 між середовищами
(node виводить `start`/`end` як byte-offset у UTF-8, Rust `oxc_span::Span`
теж; для цього сніпета збіг очікуваний, але спайк цього не автоматизує —
достатньо для S1, повний golden-фікстурний parity-тест — окрема робота,
розділ «План розблокування»).

## Рішення

**Парсер живе прямо в guest-компоненті: `oxc_parser`/`oxc_ast` як звичайні
Rust-залежності crates.io в guest-крейтах лінгвіст-концернів, без host-
медіації.** Спайк підтвердив усі три передумови: збірка під `wasm32-wasip2`
без додаткової тулінгу, прийнятний розмір (навіть у дефолтному профілі,
з `opt-level="z"` — суттєво менше), точний версійний мапінг npm↔crates.io.

Правила, що випливають з фактів спайка:

1. **Пін `oxc_parser`/`oxc_ast`/`oxc_allocator`/`oxc_span` синхронно з npm
   `oxc-parser`** — точна версія (`=X.Y.Z`), не caret-діапазон (та сама
   дисципліна, що вже задокументована для `wit-bindgen` у
   `crates/plugin-lang-js/Cargo.toml`: «НЕ розширюй у caret-діапазон без
   причини»). Дзеркальний тест версій живе там, де вже є прецедент такого
   роду перевірок — `npm/scripts/lib/lint-surface/tests/` (поруч із
   `wasm-plugin-parity.test.mjs`), новий тест читає
   `npm/package.json:dependencies.oxc-parser` і Cargo-пін відповідних
   crates у Cargo-маніфестах guest-крейтів, фейлить дельта-лінт при
   розбіжності. Оновлення — рука в руку: `taze`-провайдер JS оновлює npm-пін,
   PR-чекліст (або окремий CI-крок) вимагає синхронного Rust bump.
2. **Size-budget компонента.** Спайк дає нижню межу «сам парсер, без бізнес-
   логіки» — 549 KB (`opt-level="z"`+`lto`+`strip`+`panic=abort`) / 869 KB
   (дефолтний профіль). Чинний 9-concern `plugin_lang_js.wasm` (без
   парсера) — 1,43 MB у дефолтному профілі. Бюджет для нового
   AST-концерн-крейту (guest із оновленим `[profile.release]`,
   `opt-level="z"` — рекомендація цього документа для §3.6): **2,5 MB**
   на компонент (549 KB парсер + запас під wit-bindgen glue, business-логіку
   п'яти concern-ів і майбутнє розширення), gate у contract-test-kit
   (закриває відкрите питання «бюджет розміру» з §3.6 плагінної спеки —
   конкретне число зі спайка, як там і очікувалось).
3. **Parity-дисципліна.** Той самий двигун (`oxc_parser`, та сама пінована
   версія) з обох боків ⇒ byte-exact parity технічно досяжний (на відміну
   від regex-наближення, відхиленого PR #347). Контрибуція кожного з п'яти
   concern-ів дозволяється лише ПІСЛЯ дзеркальних parity-тестів на
   фікстурах JS-оригіналу (та сама механіка `wasm-plugin-parity.test.mjs`,
   що вже гейтить дев'ять контрибуйованих concern-ів) — не «схожий», а
   ідентичний `reason`/`message`/порядок діагностик.

## Альтернативи (розглянуто й відхилено)

- **Host-mediated AST через JSON DTO** (host парсить через npm `oxc-parser`
  або napi-биндинг, передає готове AST guest-у серіалізованим). Відхилено:
  розмір DTO (повне AST великого файлу серіалізованим JSON — типово в рази
  більше вихідного джерела), подвійна серіалізація (host: AST→JSON, guest:
  JSON→структури для обходу — накладні витрати на КОЖЕН виклик, не одноразово
  як бінарний розмір), і головне — coupling: contract v3 (§3.6 плагінної
  спеки) свідомо тримає wasm-плагіни sandboxed і незалежними від host-мови;
  AST-DTO повертає JS-специфічну структуру даних у контракт, порушуючи
  «plugin ≠ npm-пакет» / «плагіни не залежать від node» (обмеження brainstorm-
  сесії 2026-07-31, розділ «Проблема» плагінної спеки).
- **tree-sitter** (інша Rust-байндингова граматика JS/TS, теж wasm-сумісна).
  Відхилено: інша граматика ⇒ інше дерево розбору, інші межі вузлів/спанів,
  інша обробка edge-кейсів (ASI, JSX-неоднозначності, TS-специфічний
  синтаксис) — byte-exact parity з JS-оригіналом (побудованим на
  oxc-parser) принципово недосяжний тим самим шляхом, яким PR #347 відхилив
  regex-наближення: «не той самий двигун» = «не той самий вивід» на
  нетривіальних фікстурах, лише інша форма розбіжності (граматична, не
  regex-лексична).
- **ComponentizeJS-міст** (JS-оригінал компілюється в wasm як є, замість
  переписування). Уже відхилено рішенням В плагінної спеки (§2, «Чистий
  брейк, без ComponentizeJS-моста») з інших причин (другий toolchain,
  node-залежність усередині компонента) — тут лише підтверджується, що це
  рішення застосовне й до п'яти AST-заблокованих concern-ів: спайк не дає
  підстав переглядати його спеціально для них.

## Наслідки

- П'ять concern-ів розблоковано для переписування в native тим самим
  шляхом (LLM-скіл `npm/skills/wasm-plugin/`), що дев'ять уже
  контрибуйованих — жодного нового host-контракту чи WIT-розширення не
  потрібно, `oxc_parser`/`oxc_ast` — звичайні Rust-залежності guest-крейту.
- Новий клас пін-дрейфу з'являється в поверхні лінту (npm `oxc-parser` версус
  Rust `oxc_parser`/`oxc_ast`/`oxc_allocator`/`oxc_span`) — потребує
  дзеркального тесту версій (розділ «Рішення» п.1) до першої контрибуції
  жодного з п'яти concern-ів, інакше тихий дрейф можливий одразу.
- Розмір wasm-компонентів зросте помітно для будь-якого guest-крейту, що
  підключає `oxc_parser` (549 KB–869 KB залежно від профілю лише на сам
  парсер) — рекомендований `opt-level="z"` у `[profile.release]` таких
  крейтів (не дефолтний, який зараз використовує workspace) і бюджет 2,5 MB
  на компонент, зафіксований як gate.
- Golden-фікстурний parity-тест (аналог `wasm-plugin-parity.test.mjs`) —
  обов'язковий передумовний крок для КОЖНОГО з п'яти concern-ів окремо, не
  один спільний тест на всі — кожен JS-оригінал має власний набір фікстур.

## План розблокування

Порядок — від найпростішого перенесення до найскладнішого, ризик росте
разом зі складністю AST-обходу оригіналу:

1. **`js/utils_imports`, `test/no-relative-fs-path`** — прямі, невеликі
   AST-оригінали (напряму на `oxc-parser`, без проміжних lib-шарів).
   Перші кандидати: найкоротший шлях підтвердити повний golden-parity-
   цикл (скіл scaffold → build → parity-тест → контрибуція) на реальному
   AST-concern-і, не лише на спайку.
2. **`js-bun-redis/imports`** — lib-шар (`redis-imports.mjs`), але без
   мультисоткарядкового control-flow сканування; наступний за складністю
   після прямих двох.
3. **`js-mssql/deps`** (`mssql-pool-scan.mjs`, 610 рядків), потім
   **`js-bun-db/safety`** (`bun-sql-scan.mjs`, 1071 рядків) — control-flow-
   чутлива детекція (guard-и, трасування `Identifier`→init через усі
   `VariableDeclarator`, обхід предків), найбільший обсяг переписування;
   groundwork (regex-наближені detect-функції) уже лежить у
   `crates/plugin-lang-js/src/lib.rs` як довідковий матеріал для бізнес-
   логіки (НЕ для парсингу — той факт, що groundwork не пройшов parity-
   гейт, не стосується коректності самої бізнес-логіки навколо AST-обходу).
