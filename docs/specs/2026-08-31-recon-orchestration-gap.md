## 1. `native.mjs` (273) — не клас, а роль

Дослівно з наведеного завдання: **сформулювати явно, а не присвоювати клас
механічно.**

`native.mjs` — JS-бік мосту `rules-core ⇄ napi` (доккомент модуля
`native.mjs:2-54`: loader napi-аддона, ланцюг кандидатів — override →
локальна збірка → підпакет `@7n/rules-<platform>-<arch>`, звірка
`contractVersion()`). Це дзеркало напряму «JS → Rust» із §2 плану
(«`npm/scripts/lib/native.mjs` завантажує napi-аддон і кличе нативні
концерни»), симетричне `crates/rules-cli/src/js_fallback.rs` (напрям
«Rust → JS»). Головна експортована функція — `loadNative()` (`:244-273`),
кешована на процес; `nativeAddonChain()`/`resolveNativeAddon()` — публічний
доступ до ланцюга кандидатів для тестів і споживачів.

**Живий, 9 продуктивних імпортерів** (перевірено грепом,
`grep -rn "native.mjs" npm/ plugins/` без `tests?/`/`.test.mjs`):

| Імпортер | Рядок | Клас цього імпортера (за трьома розвідками) |
|---|---|---|
| `npm/scripts/utils/walkDir.mjs:4` | `import { loadNative } from '@7n/rules/scripts/lib/native.mjs'` | **A** — тонка обгортка над `rules_core::scan::walk_dir`, повністю портовано (доккомент `walkDir.mjs:41-49`); 12 продуктивних споживачів по всьому репо, живе довго |
| `npm/scripts/lib/auto-worktree.mjs:7` | `import { loadNative } from './native.mjs'` | **A**, із застереженням — §2 |
| `npm/scripts/lib/changed-files.mjs:14` | те саме | **A** — теж тонкий фасад (§3.3 `2026-08-31-recon-orchestration.md`) |
| `npm/scripts/lib/lint-surface/run-detectors.mjs:19` | те саме | область `lint-surface`, здебільшого **B** (55% рядків області) |
| `npm/scripts/lib/lint-surface/render.mjs:16` | те саме | **B**, готовий Rust-порт (`rules_core::lint_render`) чекає зняття споживача (Крок 2 плану) |
| `npm/scripts/lib/lint-surface/wasm-plugins.mjs:118` | те саме | пов'язано з Д3 (wasm-плагіни → OCI) |
| `npm/scripts/lib/lint-surface/run-fix.mjs:26` | те саме | **B**, дефолтний fix-шлях (`fix_cmd.rs:9-16`) |
| `npm/scripts/lib/lint-surface/detect.mjs:14` | те саме | **B** |

**Чому це не класифікується як A/B/C/D:** класи цієї шкали описують долю
*алгоритму* файлу. У `native.mjs` немає власного алгоритму, який можна
портувати чи не портувати, — є одна функція `loadNative()` і ланцюг
резолву шляху, які самі вже existances-guard для Rust-аддона. Питання не
«чи можна це переписати на Rust» (відповідь тривіальна — це вже виклик у
Rust, просто з JS-боку виклику), а «коли останній JS-файл перестане його
кликати». Відповідь на це питання — не властивість `native.mjs`, а сума
доль восьми (тепер `walkDir.mjs` — дев'яти) імпортерів вище. Наймолодший з
них у ланцюгу — `lint-surface`, і саме там визначено (§6
`2026-08-31-recon-lint-surface.md`) єдиний файл, що зникає останнім за
визначенням: `bridge-host.mjs`. `native.mjs` — той самий клас ролі, лише
на протилежному боці мосту: він не «лишається назавжди», а зникає рівно
тоді, коли зникає останній JS-каталог, що йому дзвонить. Це та сама
природа залежності, що в завданні названо для `bridge-host.mjs`, і вона
поширюється на `native.mjs` симетрично.

**Механізм резолву** (для довідки, без класифікації — сам механізм не
підлягає «портуванню», бо це вже точка виклику Rust): `nativeAddonChain()`
(`:169-205`) обирає порядок джерел за фактом наявності
`crates/rules-napi/Cargo.toml` поруч із коренем (`isSourceTree`,
`:115-117`) — не за env-евристикою (`CI`/`NODE_ENV`). `N_RULES_NATIVE_ADDON`
(явний override) — єдине джерело без fallback (`:179-180`, навмисно: мовчазний
відкат приховав би те, що просили перевірити). Контракт звіряється
`contractVersion()` проти `EXPECTED_CONTRACT_VERSION = 2` (`:74`, `:262-269`)
— наскрізь падає лише ця розбіжність, а не невдалий `dlopen`.

## 2. `auto-worktree.mjs` (279)

**Клас: A, з явним застереженням.** Файл розпадається на дві частини з
різною історією.

### 2.1. Worktree lifecycle — уже 1:1 нативний, тонка обгортка

`ensureRunningInWorktree` (`:60-123`) і `removeAutoCreatedWorktree`
(`:252-262`) на моменти реального створення/видалення worktree звуть
`native.sanitizeWorktreeName`/`native.worktreeCreate`/`native.worktreeRemove`
(`:113-118`, `:255-256`) — тонкі napi-обгортки
(`rules-napi/src/lib.rs:73-109`) над `rules_core::worktree`
(`crates/rules-core/src/worktree.rs`), яка сама — тонка обгортка над
крейтом `mt_core` (git dep `nitra/mt-rust`). Це не незавершений порт: у
`rules-core` є повний тестовий набір паритету (`worktree.rs:130-230+`) —
`sanitize_name_matches_mt_core_vectors`, `create_dev_worktree_*`,
`remove_worktree_*`. **Ця частина вже портована й виконується нативно**
кожного разу, коли JS доходить до неї.

### 2.2. Оркестрація навколо lifecycle — не портована, але без нових поверхонь

Решта файлу — логіка, якої в Rust немає взагалі:

- git-перевірки (`git rev-parse --show-toplevel`, `git branch --show-current`,
  `git status --porcelain`, `:67-110`) — `spawnFn`-виклики;
- інтерактивний confirm через `readline` (`defaultConfirm`, `:18-27`) з
  безпечним дефолтом поза TTY;
- `bringChangesBackToOriginal` (`:174-233`) і `copyDirectoryRecursive`
  (`:135-148`) — перенесення змін з автоствореного worktree назад чистим
  копіюванням файлів (не git-операція);
- `runCommand` (`:273-279`) — синхронний спавн `bun install`/`npx @7n/n push`.

**Чому це A, не B.** Клас B у цій шкалі означає «потребує нового
host-каналу чи зміни контракту». Жоден із цих чотирьох пунктів такого не
потребує: Rust-CLI вже має прецедент читання stdin/TTY у власному процесі
(`crates/rules-cli/src/hook_cmd.rs:100-109`, `stdin.is_terminal()`) і
власного спавну git у тестах (`crates/rules-core/src/worktree.rs:112-121`,
хелпер `git()`). Копіювання файлів і спавн `bun`/`npx` — звичайні
`std::fs`/`std::process::Command`, без WIT-каналу чи зміни протоколу
мосту. Це прямий порт: тому клас **A**, попри те, що роботи тут реально
590 рядків нового Rust-коду.

Найпряміший доказ, що це саме «непортовано», а не «непортовно»: таблиця
команд `docs/specs/2026-08-31-recon-orchestration.md` §2 сама називає ці
самі три функції серед непокритого в `lint --full`: «Не покрито: глобальна
черга `--full`, **worktree-ізоляція**, progress-бар, self-upgrade
(`:41-49`)» — в одному рядку з речами, які ніхто не пропонує вважати
структурно непортовними.

### 2.3. Застереження — повне зняття файлу впирається не в код, а в блокер

`auto-worktree.mjs` має двох споживачів, не одного:

1. `npm/bin/n-rules-cli.mjs:87-91` — `case 'lint'` для `lint --full` без
   `--no-fix` (`:1899-1901, 1940, 1956`). Цей споживач зникає разом із
   JS-CLI-роутером на кроці Д1 (зріз 6) — після нього `lint --full`
   виконується Rust-бінарем напряму, і портована версія цієї логіки живе
   там.
2. `npm/skills/taze/js/orchestrate.mjs:10,16` — **ре-експортує**
   `bringChangesBackToOriginal`/`removeAutoCreatedWorktree` для власного
   auto-worktree-флоу скіла `taze`.

Другий споживач — саме той структурний блокер, який план називає в §4 п.2:
«`skills/git-reconcile/js/orchestrate.mjs` і `skills/taze/js/*` виконуються
в дереві консюмера. Навіть після ідеального зрізу 6 частина поверхні
вимагає JS-рантайму — пряма суперечність формулюванню «бінар і більше
нічого»». Доти, доки `taze`-скіл лишається JS-оркестрованим (а це
неповʼязаний блокер, не частина обсягу цього кроку), `auto-worktree.mjs`
не можна видалити цілком — його треба або лишити як є для `taze`, або
переозброїти `taze` на виклик відповідної команди майбутнього `rules-cli`
(новий канал, тобто вже клас B для ЦІЄЇ половини задачі). **Алгоритм —
клас A; повне зняття файлу — залежність від блокера §4 п.2, не від обсягу
цього кроку.**

## 3. `worktree-notice.mjs` (180) і `root-notice.mjs` (67) — клас C сьогодні

Обидва файли — чиста текстова інжекція markdown-блоків у синкнутий
`SKILL.md` (маркери `<!-- n-rules:worktree:start/end -->`,
`<!-- n-rules:root:start/end -->`), ідемпотентна вставка/заміна/видалення
регексом (`worktree-notice.mjs:164-180`, `root-notice.mjs:52-67`).
`worktree-notice.mjs` додатково транслітерує кирилицю в короткий suffix
для назви worktree-гілки (`deriveSuffix`, `:99-110`, таблиця
`CYRILLIC_TRANSLIT`, `:43-83`).

**Єдиний споживач обох — `runSync`.** Грепом підтверджено рівно два
імпортери в усьому репо, обидва в `npm/bin/n-rules-cli.mjs`:

- `:93` — `import { injectWorktreeNotice } from '../scripts/lib/worktree-notice.mjs'`
- `:95` — `import { injectRootNotice } from '../scripts/lib/root-notice.mjs'`
- виклик обох — `:964-965`, усередині гілки синку скілів `runSync`.

Жодного іншого імпортера немає (жоден плагін, жоден скіл, жоден тест поза
власним `.test.mjs`).

**Чому клас C, а не B.** `runSync` — сама частина «дефолтного sync»,
поверхні, яку план (§2 крок 3) називає без жодного Rust-контуру: «Три
поверхні з таблиці §2 без жодного Rust-контуру: дефолтний sync (…), `taze`,
`release`». Материнська розвідка (`2026-08-31-recon-orchestration.md`,
зведення §8а) уже класифікує сімʼю `sync-claude-config.mjs + runSync +
супутні` (≈2500 рядків) як **«C сьогодні»** — з явним застереженням
«Rust-контуру немає взагалі, і §12.4.1 спеки дає лише **вшивання тексту**,
а не виконавця merge-логіки». `worktree-notice.mjs`/`root-notice.mjs` — не
частина цього підрахунку (план явно виносить їх окремо в перелік
непризначеного класу), але за складом консюмерів вони буквально
«супутні»: не мають жодного споживача поза `runSync` і виконують ту саму
роль — генерують консюмер-facing текст, який CLI записує в чужий файл.

**Що каже спека зрізу 6 (§12.4.1) конкретно для цього класу консюмер-facing
контенту** (`.mdc`, `.claude-template`, `skills/`, п. 7.1а/7.3/7.4):
«CLI віддає текст, а не шлях; жодного зовнішнього процесу» → вирок
«вшивається в бінар» через `include_dir!`/`include_str!`. Але це вирок про
**дані** (готовий текстовий шаблон), а не про **алгоритм генерації**.
`worktree-notice.mjs`/`root-notice.mjs` — саме алгоритм: вони не носять
готовий текстовий блок, а обчислюють suffix із назви скіла (кирилична
транслітерація, обрізання до 10 символів), визначають наявність
frontmatter, роблять ідемпотентну заміну регексом. «Вшити текст» тут
нічого не дає — сам блок параметризований `${suffix}` на кожен скіл
(`buildNoticeBody`, `worktree-notice.mjs:117-146`), а не однаковий скрізь.
Тому висновок §12.4.1 («вшивання доречне») не покриває цей файл: потрібен
не текст, а **виконавець** тієї самої логіки регекс-інжекції — а такого
виконавця жодна спека не проектує. Це рівно формулювання, яким материнська
розвідка позначила `runSync`-родину: «C сьогодні» — не доведена структурна
непортовність, а відсутність спроектованого шляху станом на зараз.

**Наслідок:** клас цих двох файлів — не незалежний вирок, а похідна долі
`runSync`/`sync-claude-config.mjs` (Крок 3 плану, «те, що не має плану
взагалі»). Портувати їх окремо від `runSync` немає сенсу — вони не мають
власного споживача.

## 4. `ensure-tool.mjs` (592) — внутрішній устрій, не лише межа

Материнська розвідка (§4 `2026-08-31-recon-orchestration.md`) уже
встановила межу цитатами з `tool_resolve.rs`: клас **B**, бо
`rules-core` свідомо не заводить HTTP-клієнт. Нижче — розбір усього
файлу по функціях, з приміткою, яка частина справді дзеркалиться, а яка
ні.

### 4.1. Що вже спільне з Rust (не дублюється, а читається з тих самих файлів)

- `TOOLS` (`:227`, `readToolsRegistry` `:188-205`) — будується з
  `tools.json`, того самого файлу, який `tool_registry.rs:32`
  вбудовує через `include_str!`. **Дані одні, коду для читання — два.**
- `getCacheDir` (`:127-135`) ↔ `tool_resolve::tool_cache_dir`
  (`tool_resolve.rs:75-91`) — та сама пріоритетність
  (`N_CURSOR_TOOL_CACHE_DIR` override → `LOCALAPPDATA` на Windows → `~/.cache`).
- `mapArch` (`:143-152`) ↔ `tool_registry::map_arch`
  (`tool_registry.rs:118-135`) — та сама таблиця стилів
  (`actionlint`/`conftest`/дефолт).
- `renderToolTemplate` (`:177-179`) ↔ `ToolEntry::render`
  (`tool_registry.rs:158-163`) — той самий `{ver}`/`{arch}`-шаблон.
- `buildGithubDownloadUrl` (`:320-323`) ↔ `ToolEntry::download_url`
  (`tool_registry.rs:164-172`, доккомент `:164` — «порт
  `buildGithubDownloadUrl`»). **Це виправляє твердження материнської
  розвідки** — див. §5.
- `resolveCmd`/PATH-крок `ensureTool` (`:487-489`) ↔
  `tool_resolve::resolve_cmd`/`resolve_provisioned_tool`
  (`tool_resolve.rs:64-67, 122-132`) — крейт `which`.

### 4.2. Що НЕ має Rust-порту і чому — по кожній функції

| Функція | Рядки | Чому не в `rules-core` |
|---|---:|---|
| `fetchLatestVersionViaApi`/`ViaRedirect`/`fetchLatestVersion` | `:246-307` | Потребує HTTP-клієнта (`curl`-спавн через `resolveCmd('curl')`); `tool_resolve.rs:9-16` фіксує свідому відмову: «крейт лишається офлайновим детермінованим ядром лінту, а не встановлювачем тулів». Викликається лише `tool-pins-refresh.mjs` (ручний рефреш пінів), не звичайним install-шляхом (доккомент `ensure-tool.mjs:13-15`) |
| `installFromGithub` (curl+tar, атомарна публікація) | `:334-393` | Те саме — HTTP + `tar`-спавн, і додатково розпакування архіву |
| `installViaBrew`/`installViaScoop` | `:401-430` | Формально НЕ потребують HTTP (це спавн пакетного менеджера), і `route_for`/`install_natively` в `tools_cmd.rs:76-84, 158-172` це вже дзеркалить — але лише для команди `tools ensure`, не для `ensureTool()`-виклику з середини лінт-концернів |
| `checkToolPinsFreshness` | `:76-81` | Гейт свіжості пінів (30 днів) — читає `pinnedAt` з `tool-pins.json`; `tool_registry.rs:65-68` явно каже: «поле не потрібне» (Rust-бік не має гейту свіжості взагалі, лише JS-тест `tool-pins-freshness.test.mjs`) |
| `ToolProvisionError` | `:104-111` | Клас-помилка з `name`, за яким `lint-surface/detect.mjs:157` розпізнає транзієнтний збій і йде fail-open; специфічний для JS-детекторного шляху, у Rust немає еквівалентного споживача |
| `ensureHkInstall` | `:583-592` | Реєстрація git pre-commit hook через `hk install`; викликач лише `bin/n-rules.js`-раніше-існуючий шлях (сам файл тепер 8 рядків) — окрема, вужча дія, не резолв тула |
| `installWithCrossProcessLock`/`ensureToolAsync` (single-flight + `withLock`) | `:505-575` | Async-паралельний шлях для `detectAll()` — має Rust-аналог локу (`crate::tool_lock`, ADR 260716-1354), але не аналог самого `withLock`-механізму з `getFingerprint: () => null` |

### 4.3. Найважливіше уточнення — `tools ensure` сам НЕ незалежний від цього файлу

`tool_resolve.rs:29-31` каже: «Добування тулів переїжджає в окрему команду
`tools ensure`» — це читається як «провізіонінг тепер повністю нативний».
**Це неточно**, і §5 нижче показує чому: `crates/rules-cli/src/tools_cmd.rs`
для GitHub Release install-шляху (Linux завжди, Windows без scoop-manifest)
**реверс-делегує в саме цей файл** через `LazyBridge::ensure`
(`tools_cmd.rs:206-224`) → `bridge-host.mjs` `case 'ensureTool'`
(`:238-239`) → `ensureToolAsync` з `ensure-tool.mjs` (`bridge-host.mjs:213`).
Тобто `ensure-tool.mjs` живий не лише як «публічний API пакета» (доккомент
`:26-27`, «реально споживається зовнішнім `plugins/ci-github`»), а і як
**виконавець, якого сам Rust-бінар кличе назад для власної команди
`tools ensure`**.

**Клас: B, підтверджено.** Резолв (PATH → кеш) і дані реєстру — спільні з
Rust і не потребують нової поверхні. Провізіонінг (HTTP-завантаження +
розпакування + `checkToolPinsFreshness`-гейт + `ToolProvisionError`) —
потребує або (а) заведення HTTP-клієнта в `rules-core` (архітектурна зміна
свідомо відкинута доккоментарем), або (б) лишення поточного зворотного
мосту `tools_cmd.rs → bridge-host.mjs → ensureToolAsync` як постійного
рішення, а не перехідного стану. Обидва — «потребує нового host-каналу чи
зміни контракту», рівно визначення класу B.

## 5. Знахідка: документ суперечить коду — `tools ensure` не «✅ native, повністю»

`docs/specs/2026-08-31-recon-orchestration.md` §2, таблиця команд, рядок
`tools list` / `tools ensure`:

> `tools list` / `tools ensure` | **немає в JS взагалі** | ✅ native,
> повністю | — (`tools_cmd.rs`; компенсація за прибране авто-встановлення
> в native-концернах, `main.rs:60-63`)

Твердження «немає в JS взагалі» правдиве лише для команди як публічного
CLI-інтерфейсу (немає `case 'tools'` у `n-rules-cli.mjs`). Але «✅ native,
повністю» — неточно для install-шляху: `crates/rules-cli/src/tools_cmd.rs:1-24`
(доккомент модуля) сам це визнає прямим текстом:

> «GitHub Release (Linux завжди, Windows як fallback) —
> **делегується** в чинний `ensureToolAsync` через зворотний міст
> ([`crate::bridge`], операція `ensureTool`). Причина — розділ 4
> мінідизайну: писати другу реалізацію завантаження+розпакування, поки
> перша все одно потрібна непортованим JS-споживачам, означало б тримати
> їх синхронними вручну.»

Механізм перевірено по коду до кінця: `install()` (`tools_cmd.rs:283-300`)
маршрутизує за ОС (`route_for`, `:76-84`) — `Route::Brew`/`Route::Scoop`
йдуть нативним `install_natively` (`:258-271`, спавн `brew`/`scoop`
напряму), але `Route::Github` (Linux завжди, Windows-fallback при відсутньому
scoop-manifest) іде в `LazyBridge::ensure` (`:206-224`), який піднімає той
самий unix-socket-міст, що й `lint` (`crates/rules-cli/src/bridge.rs`,
`HOST_REL = "scripts/lib/lint-surface/bridge-host.mjs"`), викликає операцію
`ensureTool` (протокол-версія `2`, `bridge.rs:33-36`, «з появою операції
`ensureTool`»), яку `bridge-host.mjs:212-216` обробляє прямим
`await import('../ensure-tool.mjs')` → `ensureToolAsync(toolId)`.

**Отже, для будь-якого тула на Linux (усі 11 записів реєстру:
`hk`/`conftest`/`shellcheck`/`actionlint`/`dotenv-linter`/`opa`/`regal`/
`hadolint`/`kubeconform`/`kubescape`/`mago`) `n-rules tools ensure`
підіймає повноцінний node-процес і виконує JS-код.** Єдині справді
безбридж-шляхи — macOS (`brew`) і Windows зі встановленим scoop-manifest-ом.
Це не применшує портованість резолву (PATH/кеш) чи корисність команди — це
виправляє одне конкретне поле однієї таблиці, яке твердить «повністю» там,
де сам код-автор написав «делегується».

**Чому це важливо для кроку 4 плану (портування класу A):** якщо крок 4
візьме таблицю §2 материнської розвідки як джерело істини «що вже
нативне», він порахує `tools ensure` за вже закриту роботу. Реальний стан:
резолв закрито, провізіонінг — ні, і для Linux-мажоритарного випадку
команда сьогодні не працює без Node у `PATH` попри назву «native».

## 6. Що це дає кроку 4 плану

Клас A з цього документа — лише алгоритмічна частина `auto-worktree.mjs`
(§2.2): git-статус-гейт, confirm-флоу, copy-back-логіка, спавн
`bun install`/`npx @7n/n push`. Це реальний, обмежений обсяг роботи (≈230
з 279 рядків файлу, за вирахуванням уже нативного lifecycle-виклику), який
не потребує нових поверхонь — прямий кандидат кроку 4.

Решта цього документа — НЕ крок 4:

- `native.mjs` — не портується самостійно; зникає похідно від споживачів
  (§1);
- `worktree-notice.mjs`/`root-notice.mjs` — клас C сьогодні, чекають на
  `runSync`/Крок 3 плану (§3);
- `ensure-tool.mjs` — клас B, чекає на рішення про HTTP-контур у
  `rules-core` або постійність зворотного мосту (§4);
- виправлення таблиці §2 материнської розвідки для `tools ensure` (§5) —
  документаційний борг, не код.
