# Канал доставки native-бінаря `n-rules` — мінідизайн

**Контекст.** `docs/specs/2026-09-01-distribution-d3-d4-scope-check.md`
виміряв, що Д3 і Д4 третьої колії обидві впираються в передумову, яку
жодна з попередніх задач не описала як роботу: **у `.github/workflows/`
немає жодного НЕ-npm release**, і `n-rules plugin publish`/`fetch` (Д1/Д2,
код готовий і протестований — `crates/rules-cli/src/plugin_cmd.rs`, §2.121,
§2.134 реєстру) не викликаються жодним конвеєром. План
(`docs/plans/2026-08-31-full-rust-migration-plan.md` §5, «Крок 0») називає
це передумовою явно: «бінар має чим доїхати до консюмера (Д2 → Д1 → Д3),
тож крок 0 і третя колія — одна робота, а не дві». Ця задача — той канал.

**Форму каналу ухвалив власник — Homebrew tap `nitra/7n`** (локальний
клон `/Users/vitalii/www/7n/homebrew`, `origin` = `git.7n.ai/7n/homebrew`,
дзеркалиться на GitHub як `nitra/homebrew-7n`, звідки `brew tap nitra/7n`
і тягне за конвенцією Homebrew). Це знімає питання 1 брифу («чим
доїжджає») з проєктування — воно вже вирішено, тут лише задокументовано й
звірено з наявним кодом. Референс — прочитано, НЕ змінено:
`/Users/vitalii/www/nitra/foc/.forgejo/workflows/{release,prepare-release}.yml`,
`/Users/vitalii/www/7n/homebrew/Formula/{foc,mt,g}.rb`,
`/Users/vitalii/www/7n/homebrew/README.md`.

Мінідизайн відповідає на решту питань брифу — те, що вимірюванням наявного
коду мусить вирішити виконавець, а не взяти готовим.

## 1. Форма каналу — Homebrew tap, і чому конвеєр `n-rules` НЕ копіює `foc` дослівно

### Три прочитані прецеденти — різні за формою, бо різні за хостингом джерела

| формула | джерело репо | де хоститься реліз | формула вказує на |
|---|---|---|---|
| `foc.rb` | Forgejo (`git.7n.ai/nitra/foc`) | Forgejo Release (`git.7n.ai`) | **мірор**: `raw.githubusercontent.com/nitra/homebrew-7n/main/assets/foc/<version>/<asset>` — байти скопійовані В САМ tap-репозиторій кроком `update-homebrew`, бо анонімний доступ до Forgejo release asset-ів не гарантований так само, як GitHub |
| `mt.rb` | **GitHub** (`github.com/nitra/mt-rust`) | GitHub Release того ж репо | **напряму**: `github.com/nitra/mt-rust/releases/download/mt-v0.1.44/mt-darwin-arm64` — жодного копіювання байтів у tap, formula лише посилається |
| `g.rb` | Forgejo (`git.7n.ai/7n/g`) | GitHub Release **дзеркального** публічного репо `nitra-public/7n-g` | проміжна форма: Forgejo-репо, але релізи йдуть через окремий публічний GH-мірор саме заради простого анонімного завантаження |

**`7n-rules` — GitHub-репозиторій (`nitra/7n-rules`), як `mt-rust`, не
Forgejo-репо, як `foc`/`g`.** Це вимірюваний факт (`git remote -v` цього
чекауту), не припущення. Отже конвеєр `n-rules` мусить бути формою
**`mt.rb`**, не `foc.rb`:

- реліз-asset хоститься в GH Release **цього самого** репозиторію
  (`github.com/nitra/7n-rules/releases/download/<tag>/<asset>`) —
  жодного окремого GH-мірор-репо (як `nitra-public/7n-g` для `g`) не
  потрібно, бо джерело вже на GitHub;
- жодного OIDC-до-Forgejo-JWT ритуалу з `foc.rb`'s `ACTIONS_ID_TOKEN_REQUEST_URL`
  + `FOC_PUBLISH_HOMEBREW_AUDIENCE` — це Forgejo-специфічний механізм
  (`enable-openid-connect: true`, ключ Forgejo, не GitHub-Actions). GitHub
  Actions має власний `permissions: id-token: write` (уже використовується
  в цьому репо для npm trusted publishing, `npm-publish.yml`), але tap
  (`git.7n.ai/7n/homebrew`, Forgejo-репозиторій за виміром вище) не
  експонує GitHub OIDC endpoint — пуш формули туди вимагає звичайного
  токена-секрету (Forgejo PAT чи deploy-key), не OIDC.

### Tag-схема — окрема від наявних, за зразком `mt-v<version>`

`package-release.yml` цього репо вже займає тег-простір `@<npm-name>@<version>`
(npm-workspace релізи). `rules-cli` — не npm-пакет, це Rust-крейт-бінар,
чия версія живе в `crates/rules-cli/Cargo.toml` (незалежно від
`npm/package.json`). Тому — окремий тег-простір, дослівно за зразком
`mt-v0.1.44` (`mt-rust`, той самий клас репозиторію): **`rules-cli-v<version>`**.
Гейт «версія тега == версія `Cargo.toml`» — той самий, що `foc.rb`'s
`release.yml`: `test "$(sed …Cargo.toml)" = "${version}"`, перенесено
дослівно (єдина частина `foc.rb`, не специфічна до Forgejo).

### Дві платформи, третя — структурно поза каналом (не тимчасово)

Наявна napi-матриця (`npm-publish.yml`'s `build-native`) знає три трійки:
`darwin-arm64`/`linux-x64-gnu`/`win32-x64-msvc`. Обидва GitHub-native
прецеденти (`mt.rb`, `g.rb`) покривають РІВНО ту саму пару, що доступна
через Homebrew:

- **darwin-arm64** — `on_macos do … if Hardware::CPU.arm?` (обидва
  прецеденти);
- **linux-x64** — `on_linux do` (обидва прецеденти);
- **Intel macOS** — `odie` (`mt.rb`: «інтел-мак поки не підтримується»,
  `foc.rb`: «Intel macOS is not supported yet») — це не вигадка цієї
  задачі, а дослівний, повторюваний патерн обох еталонів, перенесений як
  є;
- **win32-x64 — структурно поза каналом, не «поки що».** Homebrew як
  пакетний менеджер **не існує на Windows** (сам факт платформи
  Homebrew, не рішення цієї задачі чи власника tap-репо). Жоден із трьох
  прочитаних прецедентів не має `on_windows` — такого блоку в Homebrew
  Formula DSL не існує. Це означає: brew tap НІКОЛИ не покриє win32-x64
  консюмерів `n-rules`, незалежно від того, скільки платформ додасть
  власник у майбутньому. Для Windows npm (`bunx`/`npx @7n/rules`)
  лишається **єдиним** каналом — і лишиться ним і після Кроку 0 плану
  (розділ 3 нижче).

## 2. Два артефакти, два незалежні транспорти — і як `.oci-dist.lock` доїжджає до консюмера

`n-rules` несе два різні класи артефактів, і Homebrew-рішення власника
явно закриває лише один із них:

| артефакт | транспорт | стан |
|---|---|---|
| сам бінар `rules-cli` | **Homebrew tap** (розділ 1) — новий канал цієї задачі | скелет workflow, не запущено |
| шість first-party wasm-плагінів | **OCI** (`n-rules plugin publish`/`fetch`, Д1/Д2, код готовий) | публікація не підключена до жодного конвеєра (звірено §2.140) — залишається окремим, паралельним транспортом, не частиною brew tap |

Це свідома, а не випадкова відмінність: wasm-компоненти — не
per-platform виконувані файли (Component Model, платформо-незалежний,
`build-wasm-plugins.mjs`'s доккомент), Homebrew formula ganhousehold лише
`bin`-артефакти. Впихати шість `.wasm`-файлів у ту саму formula
(наприклад, `resource` DSL) означало б дублювати транспорт, який Д1 вже
спроєктував (lock + digest-first цілісність, `docs/specs/2026-09-01-
wasm-plugin-lock-resolve.md`) навколо OCI, не tarball-у.

### Як `.oci-dist.lock` потрапляє до консюмера — виміряно з Д1-мінідизайну, не вигадано тут

Д1-мінідизайн (§5-6) уже фіксує це дослівно: `.oci-dist.lock` — файл **у
корені консюмер-репо**, і `n-rules` **ніколи не постачає його** — лише
дві дії пишуть у нього:

1. **`n-rules plugin fetch`** (`crates/rules-cli/src/plugin_cmd.rs`) —
   consumer-side команда: якщо консюмер хоче явно запінити конкретний
   third-party (чи, після Д3, first-party) плагін через `package`+
   `requirement`, він сам запускає `n-rules plugin fetch --lock
   .oci-dist.lock --registry … --package … --requirement …` на своїй
   машині чи у своєму CI — команда trust-on-first-use додає запис.
2. **Ніхто інший.** Д1-мінідизайн §4 явно забороняє автоматичний виклик
   `fetch` із JS («той самий принцип, що вже застосований до
   `ensure-tool.mjs`»): PATH → кеш → явний hard-fail з підказкою команди,
   не побічний ефект резолву.

**Для шести first-party плагінів СЬОГОДНІ (до Д3) `.oci-dist.lock`
взагалі не потрібен** — вони йдуть офлайн-каналом `builtin-pins.json`
(`{name, file, sha256}`, вбудований у npm-пакет, `npm/wasm-plugins/`,
жодної мережі). OCI-канал (`wasm-plugin-oci-publish.yml`, розділ 3) —
підготовка для Д3, коли `builtin-pins.json` «переродиться» в
lock-записи (Д1-мінідизайн §3: «lock замінює `builtin-pins.json` — робота
Д3, не Д1»), а не паралельний шлях, яким консюмер мусить користуватись
зараз.

## 3. Доля `npm/package.json#bin` — brew і npm співіснують, не заміняють одне одного

### Чому не перемикання, а паралельний канал

`#bin` сьогодні (`bin/n-rules.js`) — JS-CLI-роутер, який усередині кличе
native-аддон через `npm/scripts/lib/native.mjs` (dlopen).
`crates/rules-cli/src/js_fallback.rs` і далі спавнить `npm/bin/n-rules.js`
для непортованих команд (план §2, «Rust → JS»). Перемикання `#bin` на
сам бінар («Крок 0» плану) — окрема робота, і **brew tap її не вимагає й
не замінює**:

- **Windows-консюмер не має альтернативи npm взагалі** (розділ 1: Homebrew
  структурно не покриває win32-x64) — тож `npm/bin/n-rules.js` лишається
  ЄДИНИМ каналом для цієї платформи назавжди, незалежно від того, коли
  (і чи) станеться Крок 0;
- **macOS/Linux-консюмер отримує ДРУГИЙ, незалежний спосіб** запуску
  `n-rules` — `brew install nitra/7n/n-rules` дає команду `n-rules` без
  Node/npm узагалі (типовий Homebrew use-case, той самий, що `mt`/`g`/
  `foc`), паралельно до наявного `bunx n-rules`/`npx @7n/rules`. Це
  РІЗНІ консюменти (dev-машина з інтерактивним терміналом vs CI/скрипт,
  де `npm`/`bunx` уже частина оточення) — не послідовна заміна одного
  іншим.

**Висновок:** `npm/package.json#bin` лишається на `bin/n-rules.js`
незмінно і після появи brew tap. Крок 0 плану («зробити бінар вхідною
точкою для npm-пакета») — окреме питання, орієнтоване на macOS/Linux
npm-консюмерів, які хочуть, щоб сам npm-пакет запускав бінар замість JS;
воно не залежить від brew tap і не блокується ним.

### Гучна діагностика — там, де вона взагалі застосовна

Для brew-каналу «консюмер без відповідної платформи» — це вже вирішено
самим Homebrew DSL: `odie` (Intel mac) і структурна відсутність
`on_windows` (розділ 1) — гучні за визначенням, `brew install` explicitly
провалюється з повідомленням, ніякого мовчазного пропуску тут програмно
й неможливо зробити. Проєктувати для цього окрему діагностику в JS/Rust
не потрібно — Homebrew вже є тим шаром.

Гучна діагностика (`native-cli-binary.mjs`, нижче) залишається
релевантною для **іншого** сценарію — гіпотетичного майбутнього, де сам
npm-пакет `@7n/rules` (Крок 0) шукає локально встановлений/завантажений
бінар замість JS. Той самий каскад-принцип, що вже діє для napi-аддона
(`npm/scripts/lib/native.mjs`): **джерела — ланцюг кандидатів, і на
неоголошеній платформі — hard error, ніколи мовчазний JS-fallback**
(доккомент `native.mjs`). Реалізовано в
`npm/scripts/lib/native-cli-binary.mjs` (нове, ця задача):

1. `N_RULES_CLI_BIN` (той самий env, що вже використовує тестовий
   резолвер `npm/scripts/utils/test-helpers.mjs::resolveRulesCliBin`,
   тепер обидва делегують у спільну функцію — без другого джерела правди
   для того самого каскаду) — явний override, довіряється без перевірки
   існування (той самий канон, що dev/CI override для аддона).
2. Вихідне дерево репо (`crates/rules-cli/Cargo.toml` поруч) →
   `target/{release,debug}/rules-cli[.exe]`.
3. Встановлений канал (ще НЕ live) — очікуваний шлях
   `<packageRoot>/.bin-cache/rules-cli-<platform>-<arch>[.exe]`,
   задокументований як конвенція для можливого майбутнього
   postinstall-кроку; резолвер лише перевіряє цей шлях, ніколи не пише
   туди.
4. Нічого не знайдено:
   - платформа/архітектура **не** у `SUPPORTED_CLI_TARGETS`
     (`darwin-arm64`/`linux-x64`/`win32-x64` — той самий трьома, що
     napi-матриця, ШИРШЕ за brew-покриття, бо ця гілка про
     гіпотетичний npm-шлях, не про brew) → гучна помилка «платформа не
     підтримується каналом» з переліком підтримуваних трійок;
   - платформа підтримується, але жоден кандидат не існує → гучна
     помилка з підказкою (`N_RULES_CLI_BIN=…` або `cargo build --release
     -p rules-cli`), той самий текст-жанр, що вже пише `native.mjs` і
     `test-helpers.mjs::resolveRulesCliBin`.

Жодного мовчазного повернення до `bin/n-rules.js` як «фолбека» — це
прямо заборонений принцип проєкту (§ «мовчазний skip — вада»,
`feedback_fail-loud-not-silent.md`). Модуль **не підключений** до
`package.json#bin` цією задачею — лише готовий, покритий тестами на
стабах/фікстурах, для сценарію, який може й не статись (win32 однаково
лишається JS-only).

## 4. Хто й коли публікує wasm-плагіни в OCI

Не змінилось відносно попередньої редакції цього документа — Homebrew
рішення стосується ЛИШЕ бінаря (розділ 2). Д1/Д2 дали команди (`n-rules
plugin embed-manifest`/`publish`/`fetch`), але жоден workflow їх не
кличе (`grep -n "plugin publish\|plugin fetch" .github/workflows/*.yml`
→ порожньо, звірено `2026-09-01-distribution-d3-d4-scope-check.md` §3).
Ця задача додає **новий, окремий, manual-only** workflow —
`.github/workflows/wasm-plugin-oci-publish.yml`:

- тригер лише `workflow_dispatch` (жодного `push`/`schedule`) — новий
  файл не входить у список 15 `disabled_manually` воркфлоу і не вимикає
  й не вмикає жоден з них; він просто інертний, доки хтось не запустить
  його вручну;
- обов'язковий вхідний параметр `registry` (без дефолту, той самий мотив,
  що сам `plugin publish`/`plugin fetch` — гібридна вимога Д2: ядро
  публічно, плагіни можуть бути приватними, тож CI не постулює конкретний
  реєстр);
- вхідний `dry_run` (типово `true`) — доки Harbor/Zot (Рішення 9,
  `docs/specs/2026-08-31-slice6-consumer-surfaces.md`) не існує, будь-який
  ручний запуск за замовчуванням лише РОЗРАХОВУЄ реліз (`--dry-run`), не
  пушить;
- для кожного з шести `FIRST_PARTY_WASM_PLUGINS`
  (`npm/scripts/build-wasm-plugins.mjs`, який уже сам запускає
  `embed-manifest` для всіх шести — виклик не дублюється): збірка →
  `n-rules plugin publish --registry <вхід> --component <шлях>
  [--dry-run]`.

**Коли власник його вмикає насправді (поза межами цієї задачі):** коли
Рішення 9 реалізоване і має живий endpoint — тоді перший ручний запуск із
`dry_run: false` дає перший наскрізний `publish`, а наступний `n-rules
plugin fetch` (розділ 2) — перший наскрізний тест Д1 не-стабом.

## 5. Порядок: що має статись до Д3, до Д4, і чому

```
Ця задача (Homebrew workflow-скелет, OCI-publish workflow-скелет,
           npm-CLI-резолвер + гучна діагностика, обидва не підключені)
        │
        ├──► Реальний тег rules-cli-v<X.Y.Z> + перший живий прогін
        │    rules-cli-release.yml → перший реальний GH Release asset
        │    + формула в tap оновлена
        │         │
        │         ▼
        │    Д4 стає виконуваним ДЛЯ macOS/Linux-консюмерів шаблонів:
        │    14 сніпетів + `.claude/settings.json` + `$schema` можна
        │    переписати на голий `n-rules …` — канал, ВІДМІННИЙ від
        │    npm/bunx, тепер існує. Windows-рядки Д4 (якщо такі є серед
        │    14) лишаються на `bunx`/`npx` — brew туди не дотягується
        │    структурно (розділ 1), Д4 для них НЕ виконується цим
        │    каналом узагалі
        │
        └──► `wasm-plugin-oci-publish.yml` реально запущено (не
             dry-run) проти живого OCI-реєстру (Рішення 9, окрема
             інфраструктурна задача власника) + хоч один наскрізний
             `n-rules plugin fetch`
                  │
                  ▼
             Д3 стає виконуваним: `npm/wasm-plugins/` можна прибрати
             як бандл-механізм, бо lock+кеш-резолв тепер має РЕАЛЬНЕ
             джерело, а не лише протестований, але непідключений код
```

**Чому саме такий порядок, не інший:**

- Д4 не можна раніше живого brew-релізу — попередник плану
  (`2026-08-29-js-rust-migration-completion-plan.md:113-116`) прямо
  каже: «доти `n-rules` існує лише як npm-пакет, і `bunx` — єдине, чим
  його запустити» — переписаний рядок `n-rules …` (без `bunx`) впав би
  на першому ж прогоні щойно злитий (гучний CI-red). Це тепер уточнено:
  «живий канал» = живий brew tap, не абстрактний GH Release, бо саме
  brew — форма, яку ухвалив власник.
- Д3 не можна раніше живої OCI-публікації — вимір
  (`2026-09-01-distribution-d3-d4-scope-check.md` §4) показав: консюмер
  без ручних `wasmPlugins`-пінів мовчки (skip-not-crash, доккомент
  `wasm-plugins.mjs`) втратить усі шість first-party wasm-детекторів,
  якщо `builtin-pins.json` зникне раніше, ніж є куди резолвити заміну.
- Дві гілки (Д3-путь через OCI, Д4-путь через Homebrew) **незалежні одна
  від одної** — жодна не блокує іншу, обидві блокують лише спільний
  предок («ця задача» — канали й скелети). Пов'язувати їх у послідовний
  ланцюг додало б штучну залежність, якої вимір не показує.
- `$schema`/Apicurio (Рішення 7) — та сама форма залежності, що OCI для
  плагінів, але для іншого артефакта (JSON-схема, не wasm-компонент чи
  бінар): теж має статись до Д4 торкається `CONFIG_SCHEMA_URL`, і теж не
  є роботою цієї задачі (окрема інфраструктурна реалізація власника).
- Крок 0 плану (`#bin` → бінар) НЕ входить у цей ланцюг взагалі —
  розділ 3 показав, що він орієнтований на npm-консюмерів і не залежить
  від brew tap; можна робити паралельно або взагалі не робити для
  Windows-платформи, яка залишається JS-only структурно.

## 6. Що ЦЯ задача реалізує, і що чекає на дію власника

**Реалізовано цією задачею (перевірювано без мережі, без реальних
публікацій, без реального пуша в tap-репозиторій):**

- `docs/specs/2026-09-01-native-binary-distribution-channel.md` (цей
  файл) — мінідизайн, звірений із трьома прочитаними прецедентами.
- `.github/workflows/rules-cli-release.yml` — manual-only workflow
  (`workflow_dispatch`, вхід `tag` формату `rules-cli-v<X.Y.Z>`):
  - гейт версії (тег == `crates/rules-cli/Cargo.toml`, за зразком
    `foc.rb`'s `release.yml`);
  - збірка `rules-cli` на darwin-arm64 + linux-x64 (win32 структурно
    поза каналом, розділ 1);
  - `gh release create`/upload асетів `rules-cli-darwin-arm64`/
    `rules-cli-linux-x64` у GH Release ЦЬОГО репозиторію (не окремий
    мірор-репо — на відміну від `g`, бо `7n-rules` уже на GitHub);
  - генерація/оновлення `Formula/n-rules.rb` у tap-репозиторії
    (`git.7n.ai/7n/homebrew`, вимірюваний `origin` локального клону) за
    формою `mt.rb` (пряме посилання на GH Release asset, без
    копіювання байтів у tap); клонує й пушить лише за наявності
    секрету `HOMEBREW_TAP_TOKEN` (owner-provisioned, поза межею цієї
    задачі).
- `.github/workflows/wasm-plugin-oci-publish.yml` — manual-only
  workflow: публікує (за замовчуванням `--dry-run`) шість first-party
  wasm-плагінів через уже готовий Д1/Д2-код. Без змін відносно
  попередньої редакції цього документа.
- `npm/scripts/lib/native-cli-binary.mjs` — резолвер бінаря `rules-cli`
  з гучною діагностикою для гіпотетичного майбутнього npm-шляху
  (розділ 3); НЕ підключений до `package.json#bin`.
- Тести на фікстурах/стабах для резолвера (16 тестів,
  `npm/scripts/lib/tests/native-cli-binary.test.mjs`).

**Чекає на дію власника (поза межею цієї задачі):**

1. Секрет `HOMEBREW_TAP_TOKEN` (Forgejo PAT чи deploy-key з правом пушу
   в `git.7n.ai/7n/homebrew`) — без нього крок оновлення формули
   провалюється гучно (`git push` без auth), а не мовчки.
2. Перший реальний тег `rules-cli-v<X.Y.Z>` + перший ручний прогін
   `rules-cli-release.yml`.
3. Реалізація Harbor/Zot (Рішення 9) і Apicurio (Рішення 7) —
   інфраструктура, якої в репозиторії немає взагалі.
4. Реальний (не dry-run) запуск `wasm-plugin-oci-publish.yml` проти (3) +
   хоч один наскрізний `n-rules plugin fetch`.
5. Лише після (1)+(2) — Д4 (і лише для macOS/Linux-рядків; Windows
   лишається `bunx`); лише після (3)+(4) — Д3. Жодне з двох НЕ
   виконується цією задачею.
6. Повернення 15 `disabled_manually` воркфлоу — окреме рішення власника
   (план §7, «Крок 7»), не чіпається тут; нові два файли цієї задачі
   лишаються manual-only й не входять до цього переліку.
