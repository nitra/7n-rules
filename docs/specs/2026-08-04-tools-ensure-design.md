# `tools ensure` — добування зовнішніх CLI-тулів у Rust-CLI: мінідизайн

**Дата:** 2026-08-04
**Статус:** погоджено; реалізовано в цьому ж PR (розділ 9 — межі)
**Зв'язані документи:** `docs/specs/2026-07-30-rules-v2-rust-core-migration.md`
(Р11 «порт ≠ дзеркало реалізації», Р12 «інверсія мосту; нове в napi не
заводиться»), `docs/specs/2026-08-01-rules-cli-phase8-skeleton.md` (розділ 11 —
зворотний міст), `npm/scripts/lib/ensure-tool.mjs` (джерело істини про те, ЩО і
ЯК ставиться), `docs/adr/260716-1354-*` (cross-process lock навколо install).

## 1. Мета й борг, який закривається

PR #378 зробив `k8s/kubeconform` нативним і **свідомо** прибрав авто-встановлення
тула: коли `kubeconform` не резолвиться (PATH → керований кеш), концерн падає
fail-closed із install-підказкою. Це рівно чинний режим
`N_CURSOR_NO_AUTO_INSTALL`, але для цього концерну він став дефолтом. Домовлена
компенсація — окрема команда `tools ensure`, якої не існувало. Цей документ —
її мінідизайн.

Позиція межі важлива: `rules-core` лишається офлайновим детермінованим ядром
лінту (доккомент `tool_resolve.rs`), тому добування тулів — **команда CLI**, а
не побічний ефект детектора. Лінт-рантайм резолвить і чесно каже, чого бракує;
ставить — той, хто явно попросив.

## 2. Що саме треба відтворити (інвентаризація `ensure-tool.mjs`)

| Складова | Де живе сьогодні | Природа |
| --- | --- | --- |
| Реєстр `TOOLS` (11 тулів) | `ensure-tool.mjs:165-263` | дані + замикання `asset(ver)` |
| Закріплені версії | `tool-pins.json` | дані (вже єдине джерело) |
| Крок 1-2: PATH → кеш | `ensureTool:519-539` | вже портовано (`rules_core::tool_resolve`) |
| Крок 3: brew / scoop | `installViaBrew` / `installViaScoop` | спавн пакетного менеджера |
| Крок 3: GitHub Release | `installFromGithub` | curl + tar + атомарна публікація в кеш |
| Крок 4: hard-fail + підказка | `buildHint` | вже портовано (`install_hint`) |

Споживачі JS-`ensureTool` (лишаються на перехідний період): `k8s/manifests`,

`run-conftest-batch`, `lint-surface/wasm-plugins`, `tool-pins-refresh`, а також
зовнішній `plugins/ci-github` (публічний API пакета — Р6).

## 3. Т1 — реєстр тулів: одне джерело правди, дані замість коду

**Рішення.** Реєстр виноситься з JS-коду в **декларативний
`npm/scripts/lib/tools.json`**. JS-`TOOLS` тепер **похідний** від нього
(експортована форма й сигнатури не змінюються — `entry.asset(ver)`,
`entry.binFinder(ver)` будуються з рядкових шаблонів), Rust читає той самий
файл. Версії лишаються там, де були — у `tool-pins.json` (він уже єдине джерело
і його переписує `tool-pins-refresh.mjs`; змішувати реєстр із машинно
переписуваним файлом не треба).

Шаблони замість замикань: `{ver}` — закріплена версія, `{arch}` — архітектура
у стилі, який оголошує сам запис (`archStyle`: `hk` → `x86_64`/`aarch64`,
`conftest` → `x86_64`/`arm64`, `actionlint` → `amd64`/`arm64`). Це єдине, що
було в JS кодом і мусило стати даними; решта полів (`brew`, `scoop`, `github`,
`archive`, `binPath`, `tagPrefix`) уже були даними.

**Чому не інакше:**

- *Реєстр у Rust, JS питає бінар* — JS-`ensureTool` синхронний і в гарячому
  шляху лінту; змусити його спавнити ще не опублікований `rules-cli` = зробити
  залежність у зворотний бік від напряму міграції та зламати публічний
  синхронний API (Р6).
- *Реєстр у Rust + копія в JS із mirror-тестом* — це і є два джерела правди,
  просто з гейтом. Гейт ловить дрейф **після** того, як він стався; дані в
  одному файлі роблять дрейф неможливим за конструкцією.
- *Реєстр лишається кодом у JS, Rust дублює* — рівно те, від чого застерігає
  доккомент `tool_resolve.rs` («власна копія всієї таблиці розійшлась би з
  JS-каноном непомітно»).

**Як Rust отримує файл.** `include_str!` на етапі збірки (`rules-core`), не
читання з диска в рантаймі. Причини: (1) версії крейтів і `@7n/rules`
випускаються lockstep (Р7), тож дрейф між вкомпільованою копією й
опублікованим пакетом неможливий у межах релізу; (2) команда працює й тоді,
коли корінь пакета не резолвиться (standalone-бінар); (3) немає нового
рантайм-шляху, який треба було б окремо гейтити fail-closed.

**Гейт.** Крос-мовний parity-тест `tools-registry-parity.test.mjs`: `rules-cli
tools list --json` проти JS-`TOOLS` + `tool-pins.json` — повний запис кожного
тула, включно з **відрендереним для поточної архітектури** `asset` і `binPath`.
Тобто перевіряється не лише збіг даних, а й збіг `mapArch` обох мов.

## 4. Т2 — GitHub Release: делегація в JS на перехідний період

**Рішення.** `brew`/`scoop` — нативно в Rust. Шлях «GitHub Release» (Linux
завжди; Windows як fallback) на перехідний період **делегується в чинний
JS-`ensureToolAsync`** через уже наявний ЗВОРОТНИЙ МІСТ (`bridge-host.mjs`,
нова операція `ensureTool`).

**Чому не свій HTTP і не крейт-стек прямо зараз.** Р11 п.1 каже: зрілий крейт
виграє в ручного порту — і саме тому варіант «написати свій HTTP» не
розглядався взагалі. Але вибір стоїть не між «свій HTTP» і «крейт», а між
«ще одна реалізація» і «нуль реалізацій»:

- варіант A (`ureq` + `flate2`/`tar`/`xz2`) — ~5 нових крейтів у графі
  `rules-core`/`rules-cli` разом із TLS-стеком, нові рядки в `deny.toml`/
  ліцензійному гейті, і — головне — **третя** реалізація того самого
  завантаження (JS-канон нікуди не дівається, поки його кличуть 7 споживачів
  розділу 2);
- варіант B (спавн `curl`+`tar`, як у JS) — дзеркало реалізації, проти якого
  прямо спрямований Р11 («порт ≠ дзеркало»), і без жодної переваги над A;
- варіант C (делегація) — нуль нових реалізацій, нуль нових залежностей,
  поведінка за конструкцією байт-у-байт та сама, що в лінту сьогодні
  (атомарна публікація в кеш, `ToolProvisionError`, ретраї лишаються в одному
  місці). Ціна — ~40 мс старту рантайму на прогін (вимір зрізу 4 фази 8) проти
  секунд самого завантаження, тобто шум.

Р12 цей вибір не порушує, а виконує буквально: «непортовані JS-частини
виконуються як дочірні процеси Rust-CLI, і залишок скорочується з кожним
портом». Нової JS-**поверхні** не заводиться — додається одна операція в уже
наявний host мосту, який для того й існує.

**Критерій виходу.** Коли останній JS-споживач `ensureTool` із розділу 2 буде
портований, реалізація завантаження переїжджає в Rust варіантом A (тоді це
буде єдина реалізація, а не третя), а операція мосту й `ensure-tool.mjs`
видаляються разом.

## 5. Т3 — brew/scoop нативно

Спавн пакетного менеджера — це `Command::new("brew").args(["install", …])` і
повторний резолв; жодного обходу обмежень Node тут немає (Р11 п.2), тож код
переїжджає в Rust як є. Windows: `scoop` → при відсутності scoop або запису
`"scoop": null` → та сама делегація, що й Linux (дзеркало `try/catch` у
`autoInstall`).

## 6. Т4 — cross-process лок

**Рішення.** Лок відтворюється в Rust як **підмножина взаємовиключення**
`withLock` (`mkdir`-лок + `owner.json` + перевірка живості PID + stale-поріг +
polling), з тим самим ключем `ensure-tool/<toolId>` і тим самим каталогом
стану (`<git-common-dir>/n-rules/<key>`, fallback
`node_modules/.cache/n-rules/<key>`). Тим самим — це **той самий лок**, що бере
JS: паралельні `tools ensure` (Rust) і `lint`, який дійшов до `ensureToolAsync`
(JS), взаємно виключаються, а не тупцюють по спільному `brew`/кешу.

Fingerprint-дедуп і `result.json` НЕ портуються: у JS вони теж вимкнені для
цього ключа (`getFingerprint: () => null`) — механізм призначений для повторних
CLI-команд на незмінному дереві, а тут потрібна лише взаємовиключність.
`onWaitTimeout: 'fail'` дзеркалиться (fail-closed після 20 хв).

**Пастка, яку треба тримати в голові (deadlock).** Делегований шлях (розділ 4)
викликає JS-`ensureToolAsync`, який **сам** бере цей лок. Тому Rust тримає лок
**лише навколо нативного (brew/scoop) install**, і НЕ тримає його під час
делегації. Інакше — самоблокування на 20 хв і fail-closed. Це зафіксовано
доккоментом у `tools_cmd.rs` і тестом на те, що делегований шлях лока не бере.

## 7. Т5 — поверхня команди

```
n-rules tools list [--json]
n-rules tools ensure [<tool>…] [--check]
```

- `tools list` — read-only інвентар: тул, закріплена версія, резолвлений шлях
  (або «—»), маршрут встановлення для поточної ОС. Завжди exit 0 (це відповідь
  на питання «який стан?», а не вердикт). `--json` — машинна форма, вона ж
  предмет parity-тесту.
- `tools ensure` без аргументів — усі задекларовані тули; з аргументами — лише
  названі (невідоме імʼя = usage-помилка з переліком відомих, exit 2).
- `tools ensure --check` — той самий обхід **без мутацій**: доповідає, чого
  бракує, і виходить 1, якщо бракує хоч чогось.

**Чому і `list`, і `--check`, а не щось одне.** Це два різні питання. `list` —
«покажи стан» (людині/скрипту, завжди 0, легко парситься). `--check` — «усе
готово?» (гейт: відповідь у **exit-коді**, той самий обхід і той самий вивід,
що в реального `ensure`, тільки без install). Спільного коду майже 100 %:
`--check` — це `ensure` з вимкненим кроком мутації, а `list` — той самий
резолв із іншим рендером; окремими вони коштують десятки рядків, а зливати їх
в одну команду означало б або дати `list` вердиктний exit-код (і зламати
`tools list | …` у скриптах), або змусити гейт парсити текст.

**Exit-коди** (узгоджено з `lint`): `0` — усе на місці / встановлено; `1` —
чогось бракує (`--check`) або install не вдався; `2` — usage (невідомий тул чи
прапорець).

**`N_CURSOR_NO_AUTO_INSTALL` і явність.** Змінна означає «не став нічого за
моєю спиною». `tools ensure` — не «за спиною», а прямий запит користувача, тому
команда виконує install попри неї (і знімає її для делегованого дочірнього
процесу, інакше JS відмовився б). Хто хоче лише подивитись — має `--check` і
`list`. Свідома, задокументована різниця з лінт-рантаймом, який змінну шанує.

## 8. CI

Чесна картина на сьогодні:

- Єдиний fail-closed концерн — `k8s/kubeconform`; у **цьому** репо його план
  порожній (глоб `k8s/**/*.yaml` матчить лише шляхи від кореня, а такої теки
  тут немає), тож жоден чинний прогін ним не падає. Крок `tools ensure` у
  `lint-repo.yml`/`lint-js.yml` сьогодні не потрібен — і не додається, бо
  коштував би там повної Rust-збірки заради no-op.
- `test.yml` уже збирає `rules-cli`, тому крок додається саме туди:
  `rules-cli tools ensure kubeconform`. Він виконує подвійну роботу —
  (1) гарантує тул на раннері для будь-якого майбутнього прогону, що його
  потребує, і (2) **перевіряє саму команду на реальному Linux-раннері рівно
  тим шляхом, який делегується в JS** (GitHub Release), чого стаби в
  юніт-тестах не покривають.
- Consumer-CI (`plugins/ci-github`) не чіпається: `rules-cli` ще не
  публікується в платформних пакетах, тож викликати там нічого. Це записана
  межа, а не забутий крок.

## 9. Межі цього PR

- Завантаження GitHub Release у Rust **не** реалізовано (свідомо, розділ 4) —
  на Linux `tools ensure` без встановленого тула вимагає доступного JS-рантайму
  й пакета `@7n/rules` поруч; без них команда падає з чіткою помилкою мосту.
- `ensureHkInstall` (реєстрація git-хука) до `tools ensure` не переїжджає — це
  не добування тула.
- JS-`ensureTool` лишається чинним для 7 споживачів розділу 2; його видалення —
  окремий зріз після їх портування.
- `tools list` не показує «версія встановленого бінарника» (лише закріплену):
  це вимагало б спавна кожного тула з різними прапорцями версії — окрема
  задача з власним реєстром, якщо колись знадобиться.
